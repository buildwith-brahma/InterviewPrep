Part 1 — Cloud concepts

What cloud computing is Basic

Cloud computing is on-demand access to computing resources (servers, storage, databases, networking, software) over the internet with pay-as-you-go pricing. You rent capacity from a provider instead of buying and running hardware.

Characteristic (NIST)Meaning
On-demand self-serviceProvision resources yourself in minutes through portal, CLI or API
Broad network accessAvailable over the network from many device types
Resource poolingProviders serve many customers from shared hardware (multi-tenancy)
Rapid elasticityScale out and in quickly, even automatically
Measured serviceUsage is metered and billed

Benefits and trade-offs

Benefits

  • No upfront capital cost (CapEx → OpEx)
  • Elastic scale and global reach
  • Managed services reduce operations work
  • Built-in resilience and security tooling
  • Fast experimentation

Trade-offs

  • Costs can grow unnoticed without governance
  • Vendor lock-in and skills dependency
  • Shared responsibility: misconfiguration is your risk
  • Latency and egress fees for chatty designs
  • Compliance and data-residency questions

Deployment models

  • Public cloud: shared provider infrastructure (Azure, AWS, GCP).
  • Private cloud: dedicated to one organisation (on-prem or hosted).
  • Hybrid: on-premises plus public cloud connected (Azure Arc, AWS Outposts, VPN/ExpressRoute/Direct Connect).
  • Multi-cloud: more than one provider; adds portability but also complexity.

Containers in two minutes (Docker)

A container packages an app and its dependencies into an image that runs the same everywhere, sharing the host kernel (lighter than a VM). A registry stores images; an orchestrator (Kubernetes) schedules, scales and heals containers.

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /out

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /out .
ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "ShopApi.dll"]

Object storage essentials

  • Access tiers: hot, cool/infrequent, archive. Use lifecycle rules to move or delete data automatically.
  • Redundancy: LRS/ZRS/GRS (Azure) or single-AZ/multi-AZ/cross-region replication (S3). Choose by RPO and cost.
  • Access: keep buckets private. Share with pre-signed URLs / SAS tokens (time-limited) or managed identities, never with public containers by default.
  • Versioning, soft delete, immutability (WORM) protect against deletion and ransomware.
// Azure.Storage.Blobs, using a managed identity (no secrets in code)
var svc = new BlobServiceClient(new Uri("https://shopstore.blob.core.windows.net"), new DefaultAzureCredential());
var container = svc.GetBlobContainerClient("invoices");
await container.UploadBlobAsync($"{orderId}.pdf", pdfStream);

// Time-limited download link (SAS) instead of making the container public
var sas = container.GetBlobClient($"{orderId}.pdf")
                   .GenerateSasUri(Azure.Storage.Sas.BlobSasPermissions.Read, DateTimeOffset.UtcNow.AddMinutes(15));

  • Least privilege: grant the minimum actions on the narrowest scope; review regularly.
  • No long-lived keys in code or repos. Use managed identities/roles locally with DefaultAzureCredential/SSO, and secret stores in CI.
  • MFA for all humans, break-glass accounts protected, and separate admin and daily accounts.
  • Encrypt in transit (TLS) and at rest (provider-managed or customer-managed keys). Audit with activity logs (Azure Activity Log, CloudTrail).

The usual cloud breachesPublic storage buckets, leaked access keys in Git, over-broad admin roles, open management ports (RDP/SSH to the internet), unpatched VMs, and databases with public endpoints. Almost all are configuration mistakes on the customer side.

Common patterns

  • Queue-based load levelling: producers enqueue; workers drain at their own pace.
  • Cache-aside: read cache, on miss read DB and populate; set TTLs.
  • Strangler fig: migrate a legacy app piece by piece behind a proxy (useful for AngularJS or monolith modernisation).
  • Circuit breaker, bulkhead, retry with jitter for resilience.
  • Event-driven: publish events; consumers react independently (Service Bus/Event Grid, SNS/SQS).

Hands-on project: deploy API + SPA Practice

  1. Create a free account; set a budget alert first. Create a resource group and tag it.
  2. Deploy your ASP.NET Core API to App Service (or a container to Container Apps); turn on HTTPS only and a system-assigned managed identity.
  3. Create Azure SQL (or RDS) with a private endpoint or firewall rule for your IP; keep the connection string in Key Vault, read via managed identity.
  4. Build the React/AngularJS front end and host the static files in Blob Storage static website / Static Web Apps (or S3 + CloudFront) behind a CDN; set the API CORS origin.
  5. Add Application Insights, an availability test and two alerts (5xx rate, response time).
  6. Describe it in Bicep/Terraform, add a GitHub Actions pipeline with OIDC, then delete the resource group to stop costs.
Part 6 — Interview preparation

Self-test quiz Practice

Ten questions. Pick an answer and read the explanation.

Cloud interview questions Prep

Filter by topic, expand a question and try to answer it aloud first.

IaaS vs PaaS vs SaaS vs serverless? concepts

They differ in what you manage. IaaS: OS and up. PaaS: just the app and data. Serverless/FaaS: only functions, scale-to-zero. SaaS: just configuration. More managed means less control but less operational work.

What is the shared responsibility model? concepts

The provider secures the cloud itself (facilities, hardware, hypervisor); the customer secures what they put in it (data, identities, configuration, and the OS/apps depending on the service model).

Region vs availability zone vs edge location? concepts

A region is a geographic area; zones are isolated data centres inside it for high availability; edge locations are small points of presence close to users for caching and acceleration.

What is elasticity vs scalability? concepts

Scalability is the ability to handle more load by adding resources; elasticity is doing it automatically and releasing them when load drops, so you pay for what you use.

VM, container or serverless: how do you choose? build

Prefer the most managed option that fits: SaaS/PaaS, then serverless for event-driven or spiky work, containers for portable services needing more control, VMs for legacy or OS-level needs. Consider cold starts, execution limits, cost at steady load and team skills.

Blob/S3 storage vs a database? build

Object storage holds large unstructured files cheaply with a simple key/HTTP API; databases handle structured data with queries and transactions. Typical design stores files in object storage and keeps metadata plus the URL/key in the database.

How do you deploy an ASP.NET Core app to Azure? build

Publish and deploy to App Service (or a container to Container Apps/AKS) through a CI/CD pipeline; configure settings and connection strings in app settings/Key Vault via managed identity; use deployment slots for zero-downtime swaps; enable Application Insights; scale with rules.

How do you reduce serverless cold-start impact? build

Smaller packages, lighter startup, provisioned/premium plans or warm instances, ReadyToRun/AOT for .NET, avoid heavy initialisation in the handler, and keep latency-sensitive paths on always-on compute.

How do you keep secrets out of code? sec

Use a secret store (Key Vault / Secrets Manager) accessed through a managed identity or role, inject configuration at runtime, rotate regularly, scan repos for leaks, and use OIDC federation instead of stored cloud keys in CI.

What is the principle of least privilege in cloud IAM? sec

Give each identity only the permissions it needs, on the smallest scope, for the shortest time. Prefer roles over users, review access, and use conditional access and MFA.

How would you secure a database in the cloud? sec

Private endpoint or private subnet, no public access, firewall/NSG rules, Entra ID/IAM authentication with managed identities, TDE/encryption with managed keys, TLS, auditing, backups with restore tests, and least-privilege database roles.

Security group vs NACL (or NSG)? sec

Security groups/NSGs are stateful firewalls on instances/NICs (return traffic allowed automatically). AWS NACLs are stateless subnet-level rules evaluated in order. Use security groups as the main control.

How do you design for high availability? ops

Remove single points of failure: multiple instances across zones behind a load balancer, stateless services, zone-redundant managed databases, health probes, automatic restart/scale, and retries with circuit breakers. Test failover regularly.

Explain disaster-recovery options and how you pick one. ops

Backup/restore, pilot light, warm standby, active-active: increasing cost and decreasing RTO/RPO. Pick from business-defined RTO/RPO and the cost of downtime, and rehearse the runbook.

What is blue-green vs canary deployment? ops

Blue-green keeps two environments and switches all traffic at once with instant rollback. Canary sends a small percentage of traffic to the new version first, watching metrics before ramping up.

A cloud bill doubled this month. What do you do? ops

Use cost analysis grouped by service, resource group and tag to find the change; check for forgotten resources, scaling loops, data egress, logging volume or a new environment; add budgets and alerts; right-size, schedule shutdowns, and assign cost owners via tags.

Design a scalable, resilient web application on Azure or AWS. design

CDN/WAF → load balancer → stateless app tier in 2-3 zones with autoscaling → managed database zone-redundant with read replicas and a cache; queue + workers for async tasks; blob/S3 for files; private networking and managed identities; IaC and CI/CD; monitoring and alerts; DR in a second region per RTO/RPO. Explain trade-offs and cost.

How do you handle sessions when scaling out? design

Make servers stateless: use JWT or cookie-based tokens and a shared cache (Redis) or database for server-side session data. Avoid sticky sessions unless unavoidable.

How would you migrate a legacy on-premises app? design

Assess and prioritise with the 6 Rs; start with rehost or replatform for quick wins, refactor where value justifies it; migrate data with minimal downtime (replication, cutover plan); establish landing zone, networking, identity and governance first; validate performance and cost; decommission the old system.
