Part 1 — Foundations and hosting

What is ASP.NET Core? Basic

ASP.NET Core is Microsoft's open-source, cross-platform, high-performance framework for building web applications, APIs, real-time apps and microservices on .NET. It is a ground-up redesign of the older Windows-only ASP.NET (System.Web).

Why was it rebuilt?Classic ASP.NET was tied to IIS and the monolithic System.Web assembly, so every app paid for features it never used, could not run on Linux or in containers, and was hard to test. ASP.NET Core is modular (you add only the middleware you need), host-agnostic (own web server, Kestrel), has built-in DI/configuration/logging, and is dramatically faster.

Hosting: the Host, Kestrel and reverse proxies Basic

An ASP.NET Core app is really a console application that builds a Host. The host owns the app's lifetime and wires up DI, configuration, logging and the web server that listens for HTTP.

The Generic Host

A reusable object (IHost) that starts and stops hosted services (IHostedService), handles graceful shutdown (Ctrl+C / SIGTERM), and exposes DI, config and logging. The web server is just one hosted service. The same host runs background Worker apps with no HTTP at all.

Kestrel

The default cross-platform, managed web server: async I/O, HTTP/1.1, HTTP/2, HTTP/3, TLS, WebSockets. It receives bytes from the socket, parses them into an HttpContext and runs your middleware pipeline.

Program.cs: what WebApplication actually does Basic

Since .NET 6 the entire startup lives in one file. Program.cs has two phases with a hard boundary at builder.Build(): first you register services, then you configure the request pipeline.

// ---- PHASE 1: build the service container and configuration ----
var builder = WebApplication.CreateBuilder(args);
//   CreateBuilder() already: sets content root, loads configuration
//   (appsettings.json, appsettings.{Env}.json, user-secrets, env vars, command line),
//   adds console/debug logging, configures Kestrel, and enables DI scope validation in Development.

builder.Services.AddControllers();                      // register services (DI)
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(builder.Configuration.GetConnectionString("Main")));
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization();

var app = builder.Build();                              // services are now frozen; the pipeline is configured next

// ---- PHASE 2: configure the HTTP request pipeline (ORDER MATTERS) ----
if (!app.Environment.IsDevelopment()) { app.UseExceptionHandler("/error"); app.UseHsts(); }
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseCors();
app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();                                   // endpoints
app.MapGet("/health", () => Results.Ok("healthy"));

app.Run();                                              // start Kestrel, block until shutdown

Migrating from Startup.cs (ConfigureServices / Configure)

Pre-.NET 6 projects used a Startup class: ConfigureServices(IServiceCollection) equals everything before builder.Build(), and Configure(IApplicationBuilder) equals everything after it. Both styles still work; Program.cs is simply less ceremony. Integration tests can still reach the app through WebApplicationFactory<Program> if you add public partial class Program { }.

Part 2 — The request pipeline

Request lifecycle and HttpContext Basic

Everything in ASP.NET Core revolves around HttpContext: one object per request that carries the Request, the Response, the authenticated User, the scoped RequestServices (DI), a key/value Items bag, a Connection and the RequestAborted cancellation token.

app.MapGet("/whoami", (HttpContext ctx) =>
{
    var req = ctx.Request;
    return Results.Ok(new
    {
        method   = req.Method,
        path     = req.Path.Value,
        query    = req.Query["q"].ToString(),
        agent    = req.Headers.UserAgent.ToString(),
        isHttps  = req.IsHttps,
        user     = ctx.User.Identity?.Name,
        traceId  = ctx.TraceIdentifier,
        remoteIp = ctx.Connection.RemoteIpAddress?.ToString()
    });
});

// Writing a response directly
app.Run(async ctx =>
{
    ctx.Response.StatusCode = 200;
    ctx.Response.ContentType = "text/plain";
    await ctx.Response.WriteAsync("terminal middleware", ctx.RequestAborted);
});
HttpContext is not thread-safeDo not store it in a field of a singleton or use it after the request ends (background work). Copy the values you need first. Use IHttpContextAccessor sparingly (it uses AsyncLocal).

Middleware pipeline Basic

Middleware is a component that handles a request, optionally calls the next component, and can act again on the way back. The pipeline is a chain built at startup from app.Use... calls. It is the Chain of Responsibility pattern.

Why a pipeline?Cross-cutting concerns (HTTPS, logging, errors, CORS, auth, compression) must apply to every request regardless of which endpoint handles it. Composable, ordered components keep each concern isolated, testable and optional – you pay only for what you add.

Writing middleware

// 1) Inline with Use: call next to continue; code after next runs on the way back
app.Use(async (ctx, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(ctx);                                  // downstream middleware + endpoint
    sw.Stop();
    ctx.Response.Headers["X-Elapsed-Ms"] = sw.ElapsedMilliseconds.ToString();   // NOTE: only works if headers not yet sent
});

// 2) Short-circuit: do NOT call next
app.Use(async (ctx, next) =>
{
    if (!ctx.Request.Headers.ContainsKey("X-Api-Key")) { ctx.Response.StatusCode = 401; return; }
    await next(ctx);
});

// 3) Branching
app.Map("/admin", admin => admin.Run(async c => await c.Response.WriteAsync("admin area")));
app.MapWhen(c => c.Request.Query.ContainsKey("debug"), b => b.Use(async (c, n) => { /* ... */ await n(c); }));

// 4) Class-based middleware (conventional): constructor receives RequestDelegate (singleton-lifetime deps only)
public class CorrelationIdMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext ctx, ILogger<CorrelationIdMiddleware> log)   // scoped services go on InvokeAsync
    {
        var id = ctx.Request.Headers["X-Correlation-Id"].FirstOrDefault() ?? Guid.NewGuid().ToString("N");
        ctx.Response.Headers["X-Correlation-Id"] = id;
        using (log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
            await next(ctx);
    }
}
app.UseMiddleware<CorrelationIdMiddleware>();

The standard order (memorise this)

  1. UseExceptionHandler / UseHsts – first, so it wraps everything and can catch any later failure
  2. UseHttpsRedirection
  3. UseStaticFiles – short-circuits early for files (no auth needed)
  4. UseRouting – selects the endpoint (so later middleware can read its metadata)
  5. UseCors – after routing, before auth (pre-flight requests carry no credentials)
  6. UseAuthentication – builds the user identity
  7. UseAuthorization – checks the identity against endpoint metadata ([Authorize])
  8. UseRateLimiter, UseResponseCaching, UseResponseCompression as needed
  9. Endpoints: MapControllers, MapGet, MapRazorPages, MapHub...
Order bugs you will meet
  • UseAuthorization before UseAuthentication → everyone is anonymous → 401.
  • UseCors after auth → browser pre-flight gets 401, shown as a "CORS error".
  • Writing to the response then calling next (headers already sent) → exception when a later component changes headers.
  • Exception handler registered late → errors in earlier middleware are not caught.
How the pipeline is built internally (RequestDelegate)

A RequestDelegate is delegate Task RequestDelegate(HttpContext). Each Use wraps the next one: the builder stores a list of Func<RequestDelegate, RequestDelegate> and, at Build(), folds them in reverse so the first registered becomes the outermost delegate. Calling next(ctx) simply invokes the inner delegate. The terminal delegate (when nothing matched) returns 404. There is no runtime lookup, so the pipeline is very cheap.

// What ApplicationBuilder.Build() conceptually does
RequestDelegate app = ctx => { ctx.Response.StatusCode = 404; return Task.CompletedTask; };
foreach (var component in components.Reverse())
    app = component(app);                // wrap: component(next) => new RequestDelegate
return app;                              // the outermost layer

Routing and endpoints Basic

Routing maps an incoming URL (and HTTP verb) to an endpoint – a delegate plus a bag of metadata (route pattern, HTTP methods, [Authorize], CORS policy, rate-limit policy...). Because routing selects the endpoint before authorization runs, security middleware can read that metadata.

Endpoint routing (since 3.0)

Two separate steps: UseRouting() matches the endpoint and stores it in HttpContext; Map...() endpoints execute it. In .NET 6+ minimal hosting calls UseRouting/UseEndpoints implicitly if you do not.

Matching rules

The route table is compiled into a state machine (DFA). Candidate endpoints are scored: literal segments beat constrained parameters, which beat plain parameters, then optional, then catch-all. Two equal candidates → AmbiguousMatchException.

// Minimal API routes
app.MapGet("/products", () => Results.Ok(GetAll()));
app.MapGet("/products/{id:int}", (int id) => Results.Ok(Get(id)));            // int constraint
app.MapGet("/products/{id:int:min(1)}/reviews/{page:int=1}", (int id, int page) => ...);   // default value
app.MapGet("/files/{**path}", (string path) => path);                         // catch-all keeps slashes
app.MapMethods("/ping", new[] { "GET", "HEAD" }, () => "pong");

// Route groups (.NET 7): shared prefix, filters, auth, tags
var api = app.MapGroup("/api/v1").RequireAuthorization().WithTags("v1");
api.MapGet("/orders", GetOrders);
api.MapPost("/orders", CreateOrder);

// Controller attribute routing
[ApiController, Route("api/[controller]")]            // [controller] token = class name minus "Controller"
public class ProductsController : ControllerBase
{
    [HttpGet("{id:int}", Name = "GetProduct")]
    public ActionResult<Product> Get(int id) => ...;

    [HttpPost]
    public IActionResult Create(Product p) => CreatedAtRoute("GetProduct", new { id = p.Id }, p);   // builds Location header from a named route
}

// Generate URLs from routes instead of hard-coding strings
app.MapGet("/links", (LinkGenerator links, HttpContext ctx) => links.GetPathByName(ctx, "GetProduct", new { id = 5 }));

Conventional vs attribute routing, and a note on constraints

Conventional routing (MVC views) uses one central pattern like {controller=Home}/{action=Index}/{id?}. Attribute routing (APIs) puts the template on each action – explicit and what Web APIs require. Constraints are not validation: a failed constraint produces no match (404), not a friendly 400, and constraints on APIs can hide errors. Prefer validating input and returning a ProblemDetails 400.

Results, content negotiation and formatters Mid

An endpoint returns either a plain object (serialised as JSON with 200) or a result that controls status code, headers and body. Controllers return IActionResult/ActionResult<T>; minimal APIs return IResult (via the Results / TypedResults helpers).

// Controller results
return Ok(dto);                                // 200
return Created($"/api/items/{id}", dto);       // 201 + Location
return NoContent();                            // 204
return BadRequest(ModelState);                 // 400
return NotFound();                             // 404
return Conflict(new ProblemDetails { Title = "Duplicate" });   // 409
return StatusCode(StatusCodes.Status418ImATeapot);
return File(bytes, "application/pdf", "report.pdf");           // download
return Redirect("/new-location");

// Minimal API typed results: type information flows into OpenAPI automatically
app.MapGet("/items/{id}", async Task<Results<Ok<Item>, NotFound>> (int id, AppDb db) =>
    await db.Items.FindAsync(id) is { } item ? TypedResults.Ok(item) : TypedResults.NotFound());

// Streaming large results
app.MapGet("/export", async (HttpResponse r, AppDb db) =>
{
    r.ContentType = "application/x-ndjson";
    await foreach (var row in db.Rows.AsAsyncEnumerable()) await r.WriteAsync(JsonSerializer.Serialize(row) + "\n");
});

Part 3 — Core services: DI, configuration, logging, errors, filters

Dependency injection Basic

Dependency Injection (DI) is the technique where a class receives the objects it needs (its dependencies) from the outside instead of creating them with new. ASP.NET Core has a built-in IoC container (Microsoft.Extensions.DependencyInjection) used by the framework itself, so everything – controllers, middleware, filters, hosted services – can receive services via constructors.

Why use DI?
  • Loose coupling: code depends on IEmailSender, not SmtpEmailSender; swap implementations without edits.
  • Testability: pass a fake in unit tests.
  • Lifetime management: the container creates and disposes objects at the right moment.
  • Single composition root: all wiring lives in Program.cs.
// 1) Define abstraction + implementation
public interface IClock { DateTimeOffset UtcNow { get; } }
public class SystemClock : IClock { public DateTimeOffset UtcNow => DateTimeOffset.UtcNow; }

public interface IOrderService { Task<Order> PlaceAsync(NewOrder o); }

{
    public async Task<Order> PlaceAsync(NewOrder o) { /* uses db, clock, log */ throw new NotImplementedException(); }
}

{

        }
    }

MVC and Web API controllers Basic

Why it existsControllers group related endpoints into a class and give you the full MVC feature set: filters, model binding, validation, content negotiation, and conventions such as [ApiController]. It is the most feature-rich model and the one most large codebases use.

MVC (Model-View-Controller) separates concerns: the model holds data and rules, the view renders HTML, the controller handles input and picks a result. In a Web API the "view" is simply the serialized response (JSON), so you only have controllers and models.

[ApiController]                       // 400 on invalid model, [FromBody] inference, ProblemDetails
[Route("api/[controller]")]           // api/orders
public class OrdersController : ControllerBase   // ControllerBase = no View() support, lighter
{
    private readonly IOrderService _svc;
    public OrdersController(IOrderService svc) => _svc = svc;   // constructor injection

    [HttpGet("{id:int}")]
    [ProducesResponseType<OrderDto>(200)]
    [ProducesResponseType(404)]
    public async Task<ActionResult<OrderDto>> Get(int id, CancellationToken ct)
    {
        var order = await _svc.FindAsync(id, ct);
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    public async Task<IActionResult> Create(NewOrder dto, CancellationToken ct)
    {
        var created = await _svc.CreateAsync(dto, ct);
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created);   // 201 + Location header
    }
}

Controller vs ControllerBase

ControllerBase has Ok(), NotFound(), ModelState, User. Controller adds View(), ViewBag, TempData for server-rendered HTML. Use ControllerBase for APIs.

What [ApiController] adds

Automatic 400 with ValidationProblemDetails, binding-source inference (complex type = body, simple = route/query), multipart/form-data inference, and ProblemDetails for error status codes.

How a controller action is actually invoked (internals)
  1. Routing picks an endpoint whose metadata contains an ControllerActionDescriptor.
  2. ControllerActionInvoker creates the controller through IControllerActivator, which resolves it from DI (new instance per request).
  3. Authorization, resource, then action filters run; arguments are bound and validated.
  4. The action runs; its return value is wrapped into an IActionResult; result filters run; the result executes (formatter writes the body).
  5. The controller is released (disposed if IDisposable).
Keep controllers thinA controller should translate HTTP to a call on a service and back. Business rules in the controller are untestable without HTTP and get duplicated.

Worker services and background tasks Mid

Why it existsSome work must not block a request: sending emails, processing queues, scheduled cleanup. The Generic Host can run IHostedService implementations alongside the web server, or on their own as a Worker Service (Windows Service / systemd / container).
public class CleanupWorker(IServiceScopeFactory scopes, ILogger<CleanupWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                using var scope = scopes.CreateScope();                  // hosted service is a singleton,
                var db = scope.ServiceProvider.GetRequiredService<AppDb>();   // so create a scope for scoped services
                await db.Sessions.Where(s => s.Expires < DateTime.UtcNow).ExecuteDeleteAsync(stoppingToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                log.LogError(ex, "Cleanup failed");                      // never let the loop die silently
            }
        }
    }
}
// builder.Services.AddHostedService<CleanupWorker>();

Queue pattern

Register a Channel<T> as a singleton. Controllers write to it and return 202 Accepted; a BackgroundService reads and processes. In-process queues are lost on crash, so use a durable broker (Azure Service Bus, RabbitMQ) for important work.

Scheduling

Hosted services are not a scheduler. For cron-style, retries and persistence use Hangfire, Quartz.NET, or platform features (Azure Functions timers, Kubernetes CronJob).

The context remembers entities it loaded. SaveChanges diffs them and issues INSERT/UPDATE/DELETE in one transaction.

Migrations

Concurrency

Classic pitfalls
  • N+1 queries: lazily touching navigation properties in a loop. Use Include or projection.

CORS, HTTPS and HSTS Basic

Why CORS existsThe browser's same-origin policy blocks JavaScript on https://app.example from reading responses of https://api.example. CORS is the server's way to opt in to specific cross-origin callers. It is enforced by the browser only; curl and servers ignore it, so it is not an authentication mechanism.
Preflight
builder.Services.AddCors(o => o.AddPolicy("spa", p => p
    .WithOrigins("https://app.example.com")        // exact origins; avoid AllowAnyOrigin with credentials
    .WithMethods("GET", "POST", "PUT")
    .WithHeaders("Content-Type", "Authorization")
    .AllowCredentials()                            // cookies; cannot be combined with wildcard origin
    .SetPreflightMaxAge(TimeSpan.FromMinutes(10))));

app.UseCors("spa");          // after UseRouting, before UseAuthentication/UseAuthorization

HTTPS and HSTS

  • UseHttpsRedirection() redirects HTTP to HTTPS (307/308).
  • UseHsts() sends Strict-Transport-Security, telling browsers to use HTTPS only for the max-age period; enable it in production only (it is cached by the browser, so localhost mistakes stick).
  • Behind a TLS-terminating proxy, enable UseForwardedHeaders so the app sees the original scheme/IP.
  • Locally use dotnet dev-certs https --trust.

Secrets

Common ASP.NET Core interview questions Prep

Filter by topic, expand a question and try to answer it aloud first.

What is ASP.NET Core and how does it differ from ASP.NET Framework? core

ASP.NET Core is a cross-platform, open-source, modular, high-performance framework built on modern .NET. Differences: runs on Windows/Linux/macOS, self-hosted on Kestrel (no hard dependency on IIS/System.Web), built-in DI, unified MVC/Web API, a middleware pipeline instead of HTTP modules/handlers, appsettings.json instead of web.config, side-by-side versioning and much better throughput.

What is Kestrel and do I need a reverse proxy? core

Kestrel is the cross-platform managed web server built into ASP.NET Core. It is production-ready by itself, but a reverse proxy (IIS, Nginx, YARP, a cloud load balancer) adds TLS termination, load balancing, request filtering, static content and port sharing. Behind a proxy, configure forwarded headers.

What does WebApplication.CreateBuilder set up? core

Defaults for configuration sources (appsettings, env vars, user secrets, command line), logging providers, DI container with scope validation in Development, Kestrel and IIS integration, and content root. Build() produces the WebApplication, which is both the host and the route builder.

What are environments and how are they selected? core

Environment is read from ASPNETCORE_ENVIRONMENT / DOTNET_ENVIRONMENT (default Production). Use app.Environment.IsDevelopment() for conditional middleware (developer exception page, Swagger) and appsettings.{Environment}.json for overrides.

What is the Generic Host? core

A reusable host that owns DI, configuration, logging and the lifetime of IHostedServices. The web server is just one hosted service, so the same model powers web apps, workers and console services.

What is middleware and how does ordering matter? pipeline

Middleware are components in a chain; each receives HttpContext and a next delegate, can act before and after calling it, or short-circuit. Order is the order of registration: exception handling first, then HTTPS redirect, static files, routing, CORS, authentication, authorization, then endpoints. Wrong order produces bugs such as anonymous users or missing CORS headers on error responses.

Use vs Map vs Run? pipeline

Use adds middleware that may call next. Run adds terminal middleware (no next). Map branches the pipeline for a path prefix; MapWhen branches on a predicate; UseWhen conditionally inserts middleware but rejoins the main pipeline.

Middleware vs filters – what is the difference? pipeline

Middleware runs for every request and knows nothing about MVC. Filters run inside the MVC/endpoint pipeline around action execution and can access model state, action arguments and results. Use middleware for cross-cutting HTTP concerns; filters for MVC-specific concerns.

List the filter types and their order. pipeline

Authorization, Resource, Action (with model binding between resource and action), Exception, Result. Each wraps the next like onion layers; within a type, order is global, controller, action on the way in and reversed on the way out. Exception filters handle exceptions from actions and result filters, not from other filter types.

How does routing work (endpoint routing)? pipeline

UseRouting matches the URL to an endpoint and stores it on HttpContext; middleware in between (CORS, auth) can read the endpoint metadata; UseEndpoints (implicit in .NET 6+) executes it. Route templates support constraints ({id:int}), defaults and optional segments; attribute routing is preferred for APIs.

How do you handle exceptions globally? pipeline

Register UseExceptionHandler early (or an IExceptionHandler in .NET 8) and return ProblemDetails (RFC 9457). Map known exceptions to status codes, log with a correlation id, and never expose stack traces in production.

Explain service lifetimes and the captive dependency problem. di

Transient: new instance each resolve. Scoped: one per request/scope. Singleton: one for the app. A captive dependency is a longer-lived service holding a shorter-lived one (singleton holding a scoped DbContext), which keeps it alive too long and is not thread-safe. Scope validation catches it in Development.

Why use constructor injection over service locator? di

Dependencies are explicit, the class is easy to unit test with fakes, and the container can validate the graph. Service locator (IServiceProvider.GetService everywhere) hides dependencies and fails at run time.

How do you register multiple implementations and resolve them? di

Register several for the same interface and inject IEnumerable<IPaymentProvider>; a plain IPaymentProvider gets the last registered. In .NET 8 use keyed services (AddKeyedScoped + [FromKeyedServices("stripe")]).

IOptions vs IOptionsSnapshot vs IOptionsMonitor? di

IOptions<T>: singleton, read once at startup. IOptionsSnapshot<T>: scoped, re-reads per request. IOptionsMonitor<T>: singleton with CurrentValue and OnChange. Validate with ValidateDataAnnotations().ValidateOnStart().

What is the configuration precedence? di

appsettings.json, appsettings.{Env}.json, user secrets (Development), environment variables (Section__Key), command line. Later wins. Secrets in production belong in a vault or the platform's secret store.

Controllers vs Minimal APIs – how do you choose? mvc

Controllers give the full MVC feature set (filters, model validation, conventions, formatters) and structure for large teams. Minimal APIs have lower overhead, faster startup, AOT support and less ceremony. Both share routing, DI, middleware and auth, and they can coexist.

How does model binding work, and what are binding sources? mvc

Binders populate parameters from [FromRoute], [FromQuery], [FromBody] (one per action, via input formatter), [FromHeader], [FromForm] and [FromServices]. [ApiController] infers sources. Validation then runs and populates ModelState.

What are DTOs and why not return entities? mvc

Data Transfer Objects shape what crosses the boundary. Returning EF entities leaks columns, causes serialization cycles, couples the contract to the schema and enables over-posting on input. Map with hand-written projections, Mapperly or AutoMapper.

Which HTTP status codes should an API use? mvc

200 OK, 201 Created (+Location), 202 Accepted, 204 No Content, 400 validation, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict/concurrency, 422 semantic validation, 429 rate-limited, 500 server fault. Return ProblemDetails for errors.

Razor Pages vs MVC? mvc

Both render server-side HTML with Razor. Razor Pages is page-centric (markup + PageModel together, file-based routing) and simpler for form-driven pages; MVC is controller-centric and more flexible for complex routing or shared APIs.

Blazor Server vs WebAssembly? mvc

Server runs components on the server and streams UI diffs over SignalR: small download, needs a constant connection, one circuit per user. WebAssembly runs in the browser: larger download, works offline, no server load per interaction. Auto starts with Server and switches to WASM.

Authentication vs authorization; 401 vs 403? security

Authentication identifies the caller; authorization decides permissions. 401 means "not authenticated" (missing/invalid credentials); 403 means "authenticated but forbidden".

How does JWT bearer authentication work, and what are its risks? security

The client sends a signed token; the server validates signature, issuer, audience and lifetime, then builds a principal from claims, with no server-side session. Risks: tokens cannot be revoked easily (use short lifetimes + refresh tokens), payload is readable (no secrets), theft via XSS if stored in localStorage, and weak validation settings.

Roles vs claims vs policies? security

Roles are coarse labels; claims are key-value facts about the user; policies combine requirements and handlers into reusable rules, including resource-based checks. Prefer policies for anything beyond trivial role checks.

What is CORS and is it a security feature? security

A browser mechanism relaxing the same-origin policy for allowed origins. It protects users' browsers from other sites reading responses, but it does not authenticate or protect the API from non-browser clients. Allow exact origins and avoid wildcard with credentials.

How do you prevent CSRF and XSS? security

CSRF: anti-forgery tokens, SameSite cookies, avoid cookie auth for APIs called cross-site. XSS: HTML encoding (Razor default), CSP, avoid Html.Raw, HttpOnly cookies, sanitise rich input.

What is the Data Protection API used for? security

Encrypting/signing framework data like auth cookies, anti-forgery tokens and TempData, with automatic key rotation. In multi-instance deployments persist keys to shared storage and set the same application name.

How would you store passwords? security

Never store plain text or reversible encryption. Use a slow, salted, adaptive hash (PBKDF2 through ASP.NET Core Identity, bcrypt or Argon2), with lockout, MFA and breach checks.

How do you make an ASP.NET Core API fast? perf

Measure first. Then: async I/O, efficient queries (indexes, projection, AsNoTracking, pagination), caching (memory/distributed/output), response compression, pooled HttpClient, avoid large allocations, System.Text.Json source generation, and scale out horizontally with stateless instances.

Explain caching options and invalidation. perf

IMemoryCache (per instance), IDistributedCache/Redis (shared), HybridCache (L1+L2 with stampede protection), output caching (whole responses with tags), response caching headers for browsers/CDN. Invalidate with short TTLs, versioned keys or tag eviction.

What is thread-pool starvation? perf

Too many pool threads blocked on sync-over-async calls (.Result, .Wait(), blocking I/O). New threads are injected slowly, so requests queue and latency explodes while CPU stays low. Fix by going async end to end.

How do health checks and graceful shutdown support Kubernetes? perf

Liveness tells the orchestrator to restart a dead process, readiness tells the load balancer when to send traffic. On SIGTERM the host stops accepting new requests, drains in-flight work within ShutdownTimeout, and signals hosted services to stop.

How do you test an ASP.NET Core API? perf

Unit-test services with mocks; integration-test with WebApplicationFactory and a real or containerised database; override DI registrations for external services; add contract tests from the OpenAPI document and a few end-to-end checks.

How would you version and evolve an API safely? perf

Prefer additive, backward-compatible changes. For breaking changes introduce a new version (URL or header), keep the old one during a deprecation window with Sunset headers, and document both in OpenAPI.
