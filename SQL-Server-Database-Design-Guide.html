Part 1 — Relational foundations

What a relational database is Basic

A relational database stores data in tables (relations) made of rows (records) and columns (attributes). Tables are linked by keys, and you query them with SQL (Structured Query Language), a declarative language: you say what you want and the engine's optimizer decides how.

TermMeaning
InstanceOne running SQL Server service (default or named). Hosts many databases.
DatabaseContainer of tables, views, procedures; stored in .mdf (data) and .ldf (transaction log) files.
SchemaNamespace inside a database (dbo, sales) used for grouping and permissions.
Table / row / columnEntity set / one entity / one attribute with a data type.
Primary keyColumn(s) that uniquely identify a row. Not null, unique.
Foreign keyColumn(s) referencing another table's key; enforces referential integrity.
IndexExtra structure (usually a B-tree) that speeds up lookups at the cost of writes and storage.
TransactionA unit of work that succeeds or fails as a whole (ACID).

SQL sub-languages

GroupPurposeStatements
DDL (definition)Create and change structureCREATE, ALTER, DROP, TRUNCATE
DML (manipulation)Change dataINSERT, UPDATE, DELETE, MERGE
DQL (query)Read dataSELECT
DCL (control)PermissionsGRANT, REVOKE, DENY
TCL (transaction)Group statementsBEGIN TRAN, COMMIT, ROLLBACK, SAVE TRAN

SQL Server editions and tools

  • Tools: SQL Server Management Studio (SSMS), Azure Data Studio, sqlcmd, and Visual Studio / VS Code extensions. Use Query Store and execution plans for tuning.
  • System databases: master (instance metadata), model (template for new databases), msdb (jobs, backups history), tempdb (temporary objects, sorts, row versions, recreated at every restart).

CREATE TABLE dbo.Customers (
    CustomerId   int IDENTITY(1,1) CONSTRAINT PK_Customers PRIMARY KEY,
    Email        nvarchar(256) NOT NULL CONSTRAINT UQ_Customers_Email UNIQUE,
    FullName     nvarchar(120) NOT NULL,
    CreatedUtc   datetime2(0)  NOT NULL CONSTRAINT DF_Customers_Created DEFAULT SYSUTCDATETIME()
);

CREATE TABLE dbo.Orders (
    OrderId      int IDENTITY(1,1) CONSTRAINT PK_Orders PRIMARY KEY,
    CustomerId   int NOT NULL CONSTRAINT FK_Orders_Customers REFERENCES dbo.Customers(CustomerId),
    Total        decimal(19,4) NOT NULL CONSTRAINT CK_Orders_Total CHECK (Total >= 0),
    Status       tinyint NOT NULL DEFAULT 0,
    OrderedUtc   datetime2(0) NOT NULL DEFAULT SYSUTCDATETIME()
);
Name your constraintsAuto-generated names such as PK__Orders__A1B2C3 differ per environment and make migration scripts awkward. A CONSTRAINT PK_Orders name is stable and readable in error messages.
NULL is not a valueNULL means "unknown". NULL = NULL is not true; use IS NULL. Any arithmetic or comparison with NULL yields NULL (unknown), and NOT IN with a NULL in the list returns no rows; prefer NOT EXISTS.
Part 2 — Querying with T-SQL

SELECT, filtering and logical order of execution Basic

SELECT   TOP (10) c.FullName, o.OrderId, o.Total
FROM     dbo.Orders AS o
JOIN     dbo.Customers AS c ON c.CustomerId = o.CustomerId
WHERE    o.Total >= 100
  AND    o.OrderedUtc >= '2026-01-01'
  AND    c.FullName LIKE 'A%'
ORDER BY o.Total DESC;

You write SELECT first, but the engine logically processes clauses in a different order. This explains why you cannot use a column alias in WHERE.

4. HAVINGfilter groups
→
5. SELECTcompute columns, aliases
→
6. DISTINCTremove duplicates
→
7. ORDER BYsort (can use aliases)

8. TOP / OFFSETlimit rows

Paging

-- Offset paging: page 3, 20 per page (ORDER BY is required)
SELECT OrderId, Total FROM dbo.Orders
ORDER BY OrderId
OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY;

-- Keyset ("seek") paging: fast on deep pages
SELECT TOP (20) OrderId, Total FROM dbo.Orders
WHERE OrderId > @LastSeenId
ORDER BY OrderId;
OFFSET gets slower with depthThe server still reads and discards all skipped rows. For infinite scroll or large tables use keyset paging on an indexed unique sort key.

Joins Basic

A join combines rows from two tables based on a condition. The join type decides what happens to rows with no match.

JoinReturns
INNER JOINOnly matching rows
LEFT (OUTER) JOINAll left rows + matches (NULLs on the right when none)
RIGHT (OUTER) JOINAll right rows + matches
FULL (OUTER) JOINAll rows from both, matched where possible
CROSS JOINCartesian product (n x m)
Self joinA table joined to itself (employee → manager)
CROSS / OUTER APPLYRun a table-valued expression per left row (like a lateral join): "top 3 orders per customer"
-- Self join: employee and manager
SELECT e.Name AS Employee, m.Name AS Manager
FROM dbo.Employees e
LEFT JOIN dbo.Employees m ON m.EmployeeId = e.ManagerId;

-- Top 3 most recent orders per customer using APPLY
SELECT c.FullName, x.OrderId, x.Total
FROM dbo.Customers c
CROSS APPLY (
    SELECT TOP (3) o.OrderId, o.Total
    FROM dbo.Orders o
    WHERE o.CustomerId = c.CustomerId
    ORDER BY o.OrderedUtc DESC
) AS x;
Filter placement in outer joinsA condition on the right table in WHERE (e.g. WHERE o.Status = 1) silently turns a LEFT JOIN into an INNER JOIN, because NULL rows fail the test. Put it in the ON clause to keep unmatched left rows.

Aggregation: GROUP BY and HAVING Basic

Aggregate functions collapse many rows into one value: COUNT, SUM, AVG, MIN, MAX, STRING_AGG. Every non-aggregated column in SELECT must appear in GROUP BY.

SELECT   c.CustomerId, c.FullName,
         COUNT(*)              AS Orders,
         SUM(o.Total)          AS Revenue,
         AVG(o.Total)          AS AvgOrder,
         MAX(o.OrderedUtc)     AS LastOrder
FROM     dbo.Customers c
JOIN     dbo.Orders o ON o.CustomerId = c.CustomerId
WHERE    o.OrderedUtc >= '2026-01-01'      -- filters rows BEFORE grouping
GROUP BY c.CustomerId, c.FullName
HAVING   SUM(o.Total) > 1000               -- filters groups AFTER aggregation
ORDER BY Revenue DESC;
DetailNotes
COUNT(*) vs COUNT(col)COUNT(*) counts rows; COUNT(col) skips NULLs; COUNT(DISTINCT col) counts unique non-NULL values
WHERE vs HAVINGWHERE filters rows, HAVING filters aggregated groups (cannot be replaced by WHERE)
ROLLUP, CUBE, GROUPING SETSSubtotals and grand totals in one query
Aggregates ignore NULLAVG of (10, NULL, 20) is 15, not 10

Subqueries, CTEs, temp tables and set operators Intermediate

-- CTE: a named, readable step. Recursive CTE walks hierarchies.
WITH TopCustomers AS (
    SELECT CustomerId, SUM(Total) AS Revenue
    FROM dbo.Orders
    GROUP BY CustomerId
    HAVING SUM(Total) > 1000
)
SELECT c.FullName, t.Revenue
FROM TopCustomers t
JOIN dbo.Customers c ON c.CustomerId = t.CustomerId;

-- Recursive CTE: org chart
WITH Org AS (
    SELECT EmployeeId, Name, ManagerId, 0 AS Lvl FROM dbo.Employees WHERE ManagerId IS NULL
    UNION ALL
    SELECT e.EmployeeId, e.Name, e.ManagerId, o.Lvl + 1
    FROM dbo.Employees e JOIN Org o ON e.ManagerId = o.EmployeeId
)
SELECT * FROM Org OPTION (MAXRECURSION 100);

-- EXISTS is a safe "has related rows" test
SELECT c.FullName FROM dbo.Customers c
WHERE NOT EXISTS (SELECT 1 FROM dbo.Orders o WHERE o.CustomerId = c.CustomerId);
ConstructLifetimeNotes
Subquery / derived tableOne statementInline, can be correlated
CTE (WITH)One statementReadability and recursion. It is not materialised; it is expanded like a view
Temp table #tSession / procedureStored in tempdb, has statistics and can be indexed: good for large intermediate results
Table variable @tBatchFewer statistics (deferred compilation helps in newer versions); fine for small sets
ViewPermanentStored query; an indexed view materialises it

Window functions Intermediate

A window function computes a value across a set of related rows without collapsing them (unlike GROUP BY). The OVER (PARTITION BY ... ORDER BY ...) clause defines the window.

SELECT  CustomerId, OrderId, Total, OrderedUtc,
        ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY OrderedUtc DESC) AS rn,   -- 1,2,3 (no ties)
        RANK()       OVER (ORDER BY Total DESC) AS rnk,                                -- 1,1,3 (gaps)
        DENSE_RANK() OVER (ORDER BY Total DESC) AS drnk,                               -- 1,1,2 (no gaps)
        SUM(Total)   OVER (PARTITION BY CustomerId ORDER BY OrderedUtc
                           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,
        LAG(Total)   OVER (PARTITION BY CustomerId ORDER BY OrderedUtc) AS PreviousTotal,
        NTILE(4)     OVER (ORDER BY Total) AS Quartile
FROM dbo.Orders;

-- Classic: latest order per customer
WITH x AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY OrderedUtc DESC) AS rn
  FROM dbo.Orders
)
SELECT * FROM x WHERE rn = 1;

-- Classic: Nth highest salary (2nd) without duplicates problems
SELECT DISTINCT Salary FROM (
  SELECT Salary, DENSE_RANK() OVER (ORDER BY Salary DESC) AS d FROM dbo.Employees
) s WHERE d = 2;
Interview staplesRemove duplicates (ROW_NUMBER then delete where rn > 1), top N per group, running totals, gaps and islands, previous/next row (LAG/LEAD), second-highest value.

Changing data: INSERT, UPDATE, DELETE, MERGE Basic

INSERT INTO dbo.Customers (Email, FullName) VALUES ('asha@x.com', N'Asha'), ('ben@x.com', N'Ben');

-- Get generated keys back safely (do not use @@IDENTITY)
INSERT INTO dbo.Orders (CustomerId, Total)
OUTPUT inserted.OrderId
VALUES (1, 99.50);
SELECT SCOPE_IDENTITY();                       -- last identity in this scope

UPDATE o SET o.Status = 2                      -- UPDATE ... FROM with a join
FROM dbo.Orders o JOIN dbo.Customers c ON c.CustomerId = o.CustomerId
WHERE c.Email = 'asha@x.com' AND o.Status = 1;

DELETE TOP (1000) FROM dbo.AuditLog WHERE CreatedUtc < DATEADD(DAY, -90, SYSUTCDATETIME());  -- batched delete

-- Upsert
MERGE dbo.Stock AS t
USING (VALUES (@Sku, @Qty)) AS s(Sku, Qty) ON t.Sku = s.Sku
WHEN MATCHED THEN UPDATE SET t.Qty = t.Qty + s.Qty
WHEN NOT MATCHED THEN INSERT (Sku, Qty) VALUES (s.Sku, s.Qty);
StatementRemember
DELETE vs TRUNCATE vs DROPDELETE is logged per row, can use WHERE, fires triggers. TRUNCATE removes all rows quickly, resets identity, no WHERE, no triggers. DROP removes the table itself.
Forgot WHERERun a SELECT with the same WHERE first, and wrap in BEGIN TRAN so you can ROLLBACK
MERGEConvenient but has historical bugs and race conditions; many teams use UPDATE then INSERT in a transaction with HOLDLOCK
Large changesBatch (e.g. 5,000 rows) to keep the log and locks small
Part 3 — Database design

From requirements to tables: ER modelling Basic

Good design starts with the business, not with tables. Identify entities (nouns: Customer, Order, Product), their attributes, and the relationships with cardinality (one-to-one, one-to-many, many-to-many).

Design workflow
1. Requirementswhat must be stored, which questions asked
→
2. Conceptual modelentities and relationships (ERD)
→
3. Logical modeltables, keys, normalise
→
4. Physical modeltypes, indexes, partitions
→
5. Validatetest queries, volumes, migrations
RelationshipImplementationExample
One-to-manyForeign key on the "many" sideCustomer → Orders: Orders.CustomerId
Many-to-manyJunction (bridge) table holding both keys, plus attributes of the relationshipStudents ↔ Courses via Enrollments(StudentId, CourseId, Grade)
One-to-oneForeign key with a UNIQUE constraint, or shared primary keyUser → UserProfile; split rarely-used or sensitive columns
HierarchySelf-referencing FK (ParentId), hierarchyid, or closure tableCategories, org chart

Choosing a primary key

OptionProsCons
Surrogate int/bigint identitySmall, ever-increasing, fast joins, stableMeaningless; harder to merge across systems
GUIDGenerated anywhere, no round trip, hard to guess16 bytes; random values fragment a clustered index (use sequential GUIDs)
Natural key (email, ISO country code)Meaningful, may be unique anywayCan change, can be long; keep as a UNIQUE constraint, not usually as the PK
Rule of thumbUse a small, stable, ever-increasing surrogate key as the primary key, and enforce business uniqueness separately with UNIQUE constraints.

Normalisation Basic

Normalisation removes redundancy so each fact is stored once, preventing insert, update and delete anomalies. Each normal form builds on the previous one.

FormRuleViolation → fix
1NFAtomic values, no repeating groups, each row identifiablePhones = '111, 222' → separate CustomerPhone rows
2NF1NF + no partial dependency on part of a composite keyOrderLine(OrderId, ProductId, ProductName): ProductName depends only on ProductId → move to Product
3NF2NF + no transitive dependency (non-key depends on another non-key)Customer(Id, ZipCode, City): City depends on ZipCode → ZipCode table
BCNFEvery determinant is a candidate keyStricter 3NF; resolves rare overlapping-key anomalies
4NF / 5NFNo independent multi-valued facts in one tableMostly academic; know they exist
-- Before: everything in one table
-- Orders(OrderId, CustomerName, CustomerEmail, ProductName, UnitPrice, Qty)

-- After (3NF)
Customers(CustomerId PK, Name, Email UNIQUE)
Products(ProductId PK, Name, UnitPrice)
Orders(OrderId PK, CustomerId FK, OrderedUtc)
OrderLines(OrderId FK, ProductId FK, Qty, UnitPriceAtSale, PRIMARY KEY (OrderId, ProductId))
Note UnitPriceAtSalePrices change; the price actually charged is a historical fact of the order line, so it is deliberately copied. This is correct design, not a normalisation violation.
Why normalise?One place to update a customer's address, no contradictory copies, smaller tables, constraints that actually protect the data. OLTP systems aim for 3NF.

Denormalisation, OLTP vs OLAP and common patterns Intermediate

Denormalisation deliberately adds redundancy to make reads faster or simpler. Do it with measured evidence and a plan to keep copies consistent (triggers, jobs, application logic, or computed/persisted columns).

OLTP (transactions)

  • Many small reads/writes
  • Normalised (3NF)
  • Row-store B-tree indexes
  • Latency and consistency matter

OLAP (analytics)

  • Few huge scans and aggregations
  • Star schema: fact table + dimension tables
  • Columnstore indexes
  • Throughput matters; loaded by ETL/ELT

Patterns you will meet

PatternIdeaWatch out
Soft deleteIsDeleted / DeletedUtc instead of removing the rowEvery query must filter it (use a global filter or filtered index); unique constraints need a filtered unique index
Audit / historyTemporal tables (SYSTEM_VERSIONING) keep every old row version automaticallyStorage growth; set a retention period
Lookup / enum tablesSmall table with FK (OrderStatus) vs a check constraintKeep ids stable across environments
EAV (entity-attribute-value)Flexible key-value rowsSlow, no types or constraints; prefer JSON column or sparse columns for variable attributes
Multi-tenancyTenant per database, schema, or TenantId columnAlways filter by tenant; consider Row-Level Security
Optimistic concurrencyrowversion column compared on updateHandle the 0-rows-updated case (conflict)
-- Unique email only among non-deleted rows
CREATE UNIQUE INDEX UX_Customers_Email_Active ON dbo.Customers(Email) WHERE IsDeleted = 0;

-- Optimistic concurrency token
ALTER TABLE dbo.Orders ADD RowVer rowversion;
UPDATE dbo.Orders SET Status = 3 WHERE OrderId = @Id AND RowVer = @OriginalRowVer;   -- check @@ROWCOUNT = 1

-- Temporal table
CREATE TABLE dbo.Prices (
    ProductId int NOT NULL PRIMARY KEY, Price decimal(19,4) NOT NULL,
    ValidFrom datetime2 GENERATED ALWAYS AS ROW START, ValidTo datetime2 GENERATED ALWAYS AS ROW END,
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
) WITH (SYSTEM_VERSIONING = ON);
Part 4 — Indexes and performance

Indexes Intermediate

Data pages are 8 KB. Without an index the engine must scan every page; with a suitable index it seeks through a balanced tree in a handful of page reads (usually 3-4 levels even for millions of rows).

Index typeWhat it isNotes
ClusteredThe table is the index: rows physically ordered by the key; leaf level = data pagesOne per table. Choose narrow, unique, ever-increasing (identity). The primary key is clustered by default
NonclusteredSeparate B-tree of key columns + a pointer (the clustering key) to the rowUp to 999 per table; each one slows writes and uses space
Covering (INCLUDE)Nonclustered index containing all columns the query needsAvoids key lookups
FilteredIndex over a subset (WHERE IsActive = 1)Smaller, targeted; also for unique-where-not-deleted
CompositeSeveral key columns; order mattersUsable for the leftmost prefix: equality columns first, then range, then sort
ColumnstoreColumn-oriented compressed storageAnalytics and large scans, not point lookups
Unique, Full-text, XML, SpatialSpecialisedFull-text for word search instead of LIKE '%x%'
-- Query: recent orders for a customer by status
SELECT OrderId, Total, OrderedUtc
FROM dbo.Orders
WHERE CustomerId = @c AND Status = 1
ORDER BY OrderedUtc DESC;

-- Composite + covering: equality columns first, then the sort column, others INCLUDEd
CREATE NONCLUSTERED INDEX IX_Orders_Customer_Status_Date
ON dbo.Orders (CustomerId, Status, OrderedUtc DESC)
INCLUDE (Total);

-- Find unused / missing indexes
SELECT * FROM sys.dm_db_missing_index_details;
SELECT OBJECT_NAME(object_id) AS tbl, user_seeks, user_scans, user_updates FROM sys.dm_db_index_usage_stats;
Indexes are not freeEvery INSERT/UPDATE/DELETE must maintain every index on the table. Over-indexing slows writes and bloats storage. Index for real queries (check Query Store), drop unused ones, and keep keys narrow.

Why an index is sometimes ignored (non-SARGable predicates)

Fragmentation, fill factor and statistics
  • Fragmentation: page splits leave pages half-empty and out of order. ALTER INDEX ... REORGANIZE (light, online) for ~5-30%, REBUILD for >30%. On SSDs and with smaller indexes it matters less than good statistics.
  • Fill factor: % of each leaf page filled at rebuild; lower (e.g. 90) leaves room for inserts in random-key indexes.
  • Statistics: histograms of column value distribution the optimizer uses for row-count estimates. Stale statistics cause bad plans: keep AUTO_UPDATE_STATISTICS on and update after large loads.

Execution plans and query tuning Advanced

The optimizer produces an execution plan: the operators (scan, seek, join type, sort) it will use. Read it right-to-left, top-to-bottom, and compare estimated vs actual row counts; big differences point to stale statistics or a poor estimate.

OperatorMeaningRed flag when
Index/Clustered SeekNavigates the B-tree to specific rowsSeek returning most of the table
Index/Table ScanReads every row/pageLarge table, selective predicate
Key LookupFetch missing columns from the clustered index per rowThousands of lookups → add INCLUDE columns
Nested Loops joinFor each outer row, seek innerLarge outer input
Hash Match joinBuilds a hash table of one inputSpills to tempdb (memory grant too small)
Merge JoinBoth inputs sorted on the keyForced sorts added
Sort / SpoolOrder or cache rowsWarnings, spills
SET STATISTICS IO ON;       -- logical reads per table: the main number to reduce
SET STATISTICS TIME ON;
-- Ctrl+M in SSMS shows the actual plan

-- Slowest queries from Query Store / DMVs
SELECT TOP (10) qs.total_elapsed_time / qs.execution_count AS avg_us, qs.execution_count,
       SUBSTRING(st.text, 1, 200) AS sql_text
FROM sys.dm_exec_query_stats qs CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY avg_us DESC;

Tuning checklist

  1. Find the real slow query (Query Store, Extended Events, application timing), not the one you suspect.
  2. Look at the actual plan and logical reads; compare estimated vs actual rows.
  3. Fix predicates to be SARGable; remove implicit conversions; select only needed columns (no SELECT *).
  4. Add or adjust an index (equality, range, sort, INCLUDE); then recheck reads.
  5. Watch for parameter sniffing: a plan compiled for one parameter value is bad for another. Options: OPTION (RECOMPILE), OPTIMIZE FOR, split procedures, Query Store plan forcing.
  6. Reduce round trips and rows: filter early, page, batch writes, avoid row-by-row cursors and N+1 queries.
Part 5 — Transactions and concurrency

Transactions and ACID Basic

A transaction groups statements so they succeed or fail together. SQL Server guarantees ACID:

LetterPropertyHow SQL Server provides it
AAtomicity: all or nothingTransaction log undo on rollback
CConsistency: constraints hold before and afterConstraints, keys, triggers
IIsolation: concurrent transactions do not see each other's partial workLocks or row versioning (isolation levels)
DDurability: committed data survives a crashWrite-ahead logging: log flushed to disk at commit
SET XACT_ABORT ON;       -- any runtime error rolls the whole transaction back and aborts the batch
BEGIN TRY
    BEGIN TRAN;
        UPDATE dbo.Accounts SET Balance = Balance - 100 WHERE AccountId = 1 AND Balance >= 100;
        IF @@ROWCOUNT = 0 THROW 50001, 'Insufficient funds', 1;
        UPDATE dbo.Accounts SET Balance = Balance + 100 WHERE AccountId = 2;
    COMMIT;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;
    THROW;                -- rethrow to the caller
END CATCH;
Keep transactions shortDo not hold a transaction open while waiting for user input or calling an external API. Open late, commit early, touch tables in a consistent order.

Transaction modes

  • Autocommit (default): each statement is its own transaction.
  • Explicit: BEGIN TRAN ... COMMIT/ROLLBACK.
  • Implicit: SET IMPLICIT_TRANSACTIONS ON (rare).
  • Distributed: across servers via MSDTC; avoid in cloud designs, prefer sagas and idempotent messages.

Isolation levels, locking and deadlocks Advanced

Isolation decides what one transaction may see of another. The weaker the level, the more anomalies (anomalous reads) are possible; the stronger, the more blocking.

AnomalyMeaning
Dirty readReading another transaction's uncommitted data
Non-repeatable readReading the same row twice and getting different values
Phantom readRe-running a range query and getting new rows
Lost updateTwo transactions read, then overwrite each other's change
Write skewTwo transactions read overlapping data, write different rows, and together break an invariant (both doctors go off call)

Locks and blocking

  • Lock modes: Shared (S, reads), Exclusive (X, writes), Update (U, to avoid conversion deadlocks), Intent (IS/IX, table-level signal that row locks exist).
  • Granularity: row → page → table. After about 5,000 locks the engine may escalate to a table lock.
  • Blocking = one session waits for another's lock. Diagnose with sys.dm_exec_requests (blocking_session_id) or sp_whoisactive.
A deadlock

↔
Cycle: each waits for the othernobody can proceed
↔
Tx B locks row 2needs row 1
→
Engine picks a victimerror 1205: rolled back, retry
Reduce deadlocksHow
Consistent orderAlways access tables/rows in the same sequence
Short transactionsDo less work between BEGIN and COMMIT
Right indexesNarrow the rows locked; avoid scans that lock everything
Row versioningEnable READ_COMMITTED_SNAPSHOT so readers do not block writers

ALTER DATABASE Shop SET READ_COMMITTED_SNAPSHOT ON;          -- readers use row versions
ALTER DATABASE Shop SET ALLOW_SNAPSHOT_ISOLATION ON;
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

-- Pessimistic "claim a job" without two workers taking the same row
SELECT TOP (1) * FROM dbo.Jobs WITH (UPDLOCK, READPAST, ROWLOCK) WHERE Status = 0 ORDER BY JobId;
NOLOCK is not a free speed-upIt equals READ UNCOMMITTED: you can read uncommitted, duplicated or missing rows. Prefer row versioning (RCSI) to solve reader/writer blocking.

    @From datetime2 = NULL
AS

Security

  • Least privilege: logins (server) → users (database) → roles/permissions on schemas or procedures. Never run apps as sa or db_owner.
  • Authentication: prefer Windows/Entra ID (managed identity in Azure) over SQL passwords; keep secrets in Key Vault.
  • Encryption: TLS in transit, TDE at rest, Always Encrypted for sensitive columns, dynamic data masking and row-level security for exposure control.
  • Auditing: SQL Audit / Extended Events; parameterised queries stop injection.

CAP theorem: during a network partition a distributed store must choose between consistency and availability. Many NoSQL stores choose availability with eventual consistency; relational systems on one node favour strong consistency. Most real systems use polyglot persistence: relational as the source of truth plus cache, search or document stores for specific needs.

SQL and database design interview questions Prep

Filter by topic, expand a question and try to answer it aloud first.

INNER vs LEFT vs FULL OUTER join? query

INNER keeps only matches. LEFT keeps all left rows with NULLs where no right match. FULL keeps all rows from both. Choose by which unmatched rows you must retain.

WHERE vs HAVING? query

WHERE filters rows before grouping and cannot use aggregates. HAVING filters groups after aggregation. Filter as much as possible in WHERE for performance.

DELETE vs TRUNCATE vs DROP? query

DELETE removes rows (optional WHERE, fully logged, fires triggers, keeps identity). TRUNCATE removes all rows minimally logged, resets identity, no WHERE or triggers, needs ALTER permission. DROP removes the table definition too.

UNION vs UNION ALL? query

UNION removes duplicates (extra sort/hash), UNION ALL keeps all rows and is faster. Use UNION ALL unless duplicates must be removed.

How do you find the second highest salary / delete duplicate rows? query

Use DENSE_RANK() OVER (ORDER BY Salary DESC) and select rank 2 (handles ties). For duplicates, number rows with ROW_NUMBER() OVER (PARTITION BY key ORDER BY id) in a CTE and delete rn > 1.

CTE vs temp table vs table variable? query

A CTE is a named subquery for one statement (not materialised). A temp table lives in tempdb for the session, has statistics and indexes: good for large intermediate results reused several times. A table variable is batch-scoped with limited statistics: fine for small sets.

How does NULL behave in comparisons and aggregates? query

Comparisons with NULL are unknown, so use IS NULL. Aggregates (except COUNT(*)) ignore NULLs. NOT IN with a NULL in the subquery returns nothing; use NOT EXISTS.

What is normalisation and when would you denormalise? design

Organising data to remove redundancy and anomalies (1NF-3NF/BCNF). Denormalise deliberately for read performance or reporting (star schemas, precomputed totals), with a plan to keep copies consistent, after measuring a real problem.

Primary key vs unique key vs foreign key? design

PK: unique, not null, one per table, clustered by default. Unique key: enforces uniqueness (allows a NULL), several per table. FK: references a parent key, enforcing referential integrity with cascade options.

How do you model many-to-many? design

A junction table with foreign keys to both sides (composite primary key) plus any relationship attributes (enrolment date, grade).

Surrogate vs natural keys? design

Surrogate keys (identity/GUID) are small, stable and meaningless; natural keys carry business meaning but can change or be long. Common approach: surrogate PK plus a UNIQUE constraint on the natural key.

Design the schema for an e-commerce order system. design

Customers, Addresses, Products, Categories, Orders (CustomerId, status, totals, timestamps), OrderLines (OrderId, ProductId, Qty, UnitPriceAtSale), Payments, Shipments, Inventory. Keys and constraints, indexes on foreign keys and common filters, money as decimal, UTC timestamps, soft delete or history where needed, and explain query patterns that drive indexes.

Clustered vs nonclustered index? index

Clustered defines the physical order and stores the data in its leaf pages (one per table). Nonclustered is a separate structure pointing back to the rows (many per table). Covering nonclustered indexes use INCLUDE to avoid key lookups.

A query is slow. How do you investigate? index

Reproduce with real parameters; read the actual plan and STATISTICS IO; compare estimated and actual rows; look for scans, key lookups, spills and implicit conversions; check statistics and parameter sniffing; fix predicates or add an index; re-measure. Use Query Store for regressions.

What is a SARGable predicate? index

One the optimizer can satisfy with an index seek. Wrapping the column in a function (YEAR(col), ISNULL(col,0)) or leading wildcards prevents it; rewrite as a range on the bare column.

Why not index every column? index

Each index costs storage and slows INSERT/UPDATE/DELETE, adds maintenance and plan complexity. Index based on actual query patterns; remove unused ones.

What is parameter sniffing? index

The plan is compiled for the first parameter values and reused. If later values have very different selectivity, the cached plan is poor. Fix with OPTION (RECOMPILE), OPTIMIZE FOR, better statistics/indexes, splitting logic or Query Store forcing.

Explain ACID. tx

Atomicity (all or nothing), Consistency (constraints preserved), Isolation (concurrent transactions do not interfere), Durability (committed data survives crashes via write-ahead logging).

What are isolation levels and which do you use? tx

They trade consistency against concurrency: READ UNCOMMITTED, READ COMMITTED (default), REPEATABLE READ, SERIALIZABLE, plus row-versioning SNAPSHOT/RCSI. Most web apps use READ COMMITTED SNAPSHOT to avoid reader/writer blocking, and SERIALIZABLE or UPDLOCK only for narrow invariants.

How do you detect and prevent deadlocks? tx

Capture the deadlock graph (Extended Events system_health). Prevent with consistent access order, short transactions, proper indexes, RCSI and retry on error 1205.

Pessimistic vs optimistic concurrency? tx

Pessimistic locks data while you work (UPDLOCK); safe for hot contention but blocks. Optimistic lets everyone proceed and checks at write time with a rowversion token, handling conflicts by retrying or telling the user.

What backup types exist and how do you restore to a point in time? ops

Full, differential, transaction log. Under the full recovery model restore the last full, the latest differential, then log backups with STOPAT. Define RPO/RTO and test restores.

How do you scale a database that is slowing down? ops

First optimise queries and indexes; then caching, read replicas, partitioning or archiving old data, bigger hardware (scale up), and only then sharding. Measure at each step.

SQL vs NoSQL: how do you choose? ops

Relational for structured data needing joins, transactions and reporting; NoSQL where the access pattern is simple key/document lookup at huge scale or the schema varies. Many systems use both.
