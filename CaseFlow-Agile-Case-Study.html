Business Requirement

BR-001 to BR-006 · Contoso Utilities – Customer Service Transformation Programme

1.1 Business problem

Contoso Utilities Ltd supplies energy and broadband to 4.2 million customers. About 38,000 new customer cases per month (billing disputes, meter faults, outages, complaints, service changes) are handled by 450 agents across three contact centres (Leeds, Pune, Krakow). Cases are tracked in a mixture of shared mailboxes, Excel trackers and a 14-year-old VB6/Access tool (CaseTracker) that sits on an unsupported SQL Server 2012 box.

  • No single view of a customer’s open cases; 11% of cases are duplicates.
  • Average 5.5 hours from receipt to first assignment; 18% of cases breach SLA.
  • No reliable audit trail — Internal Audit raised a High finding (AUD-2025-07); two regulator complaints could not be fully evidenced.
  • Attachments travel by e-mail and sit on personal drives (data protection risk).
  • Legacy platform leaves vendor support on 31 Dec 2026.

1.3 Proposed solution (to-be)

CaseFlow — a secure web application (Angular SPA + ASP.NET Core Web API on Azure) that gives every agent one place to create, find, assign, work and close cases, with automatic SLA tracking, e-mail notifications, role-based access, a complete audit history and live dashboards. It integrates with the enterprise CRM (customer master) and ERP/Billing (financial adjustments) and replaces the legacy tool and Excel trackers.

7.3 Architecture flows

Authentication flow (Entra ID, OIDC Authorization Code + PKCE)

  1. User opens https://caseflow.contoso.example; Angular (MSAL) detects no session and redirects to Entra ID.
  2. Entra ID authenticates the user (SSO + MFA by Conditional Access) and returns an authorization code.
  3. MSAL exchanges the code (PKCE) for an ID token and an access token for API scope api://caseflow-api/access_as_user.
  4. The HTTP interceptor adds Authorization: Bearer <JWT> to every API call.
  5. The API validates signature, issuer, audience, expiry (AddMicrosoftIdentityWebApi) and maps app roles (Agent, TeamLead, Supervisor, Compliance, Admin) to ASP.NET policies.
  6. Service-to-service calls (API → SQL, Key Vault, Blob, Service Bus) use managed identity, never passwords.

API request flow (e.g. POST /api/cases)

  1. Angular form posts JSON with X-Correlation-Id (GUID) and Idempotency-Key.
  2. Middleware pipeline: HTTPS redirect → correlation-id middleware → exception handler → auth → rate limiter.
  3. Controller binds DTO; FluentValidation runs; authorization policy CanCreateCase evaluated.
  4. MediatR CreateCaseCommand → handler calls CRM adapter (customer check), duplicate check, case-number generator.
  5. Handler writes Cases, CaseHistory and OutboxMessages in one transaction.
  6. API returns 201 Created + Location header and the case DTO; telemetry is emitted with the correlation id.

Database flow

  • Writes: EF Core in a unit of work, short transactions, RowVersion optimistic concurrency, explicit isolation READ COMMITTED SNAPSHOT.
  • Reads/search: Dapper + parameterised SQL against indexed columns; keyset pagination; reporting views read from the readable geo-replica.
  • History: every state change inserts a CaseHistory row in the same transaction as the change (append-only, no UPDATE/DELETE permission for the app login).
  • Schema changes: versioned scripts (DbUp) / EF migrations bundle executed by the release pipeline using a deployment identity.
  • Transient faults: EnableRetryOnFailure with SQL error code list; deadlock retry (error 1205) in the unit of work.

Async messaging flow (transactional outbox)

  1. Command handler stores an OutboxMessages row (e.g. CaseCreated) in the same DB transaction as the case.
  2. A background publisher (COMP-26 Outbox publisher, hosted service) reads unpublished rows and sends to the Service Bus topic case-events with MessageId = outbox id (duplicate detection ON, 10 min).
  3. Subscription notify → Notification Function (COMP-11) renders the template and sends e-mail; writes a Notifications row.
  4. Subscription erp-sync → ERP sync function posts the adjustment to ERP when a case closes with a financial outcome.
  5. Failures retry (max delivery 5, exponential back-off); then the message goes to the dead-letter queue, raising an alert for L2 to replay.
  6. Consumers are idempotent (check Notifications.MessageId / ERP reference before acting).

Error handling

  • Global exception middleware returns RFC 7807 ProblemDetails with traceId and correlationId; no stack traces to clients.
  • 400 validation (field errors), 401, 403, 404, 409 (concurrency/duplicate), 422 (workflow rule), 429, 500, 503 (dependency down).
  • Polly: retry (3, jittered), timeout (5 s), circuit breaker (5 failures / 30 s) for CRM and ERP.
  • Angular: central ErrorInterceptor, friendly toast + “Reference: correlationId” for the service desk.
  • Functions: poison messages to DLQ; unhandled exceptions logged and alerted.

Logging

  • Serilog structured JSON → Application Insights sink; enrichers: CorrelationId, UserId (hashed), Environment, Release.
  • Levels: Information for business events (CaseCreated), Warning for recoverable issues, Error for failures.
  • No PII (names, e-mails, descriptions) in logs; use case number and internal IDs.
  • Audit history (business) is stored in SQL; operational logs are in Log Analytics (retention 90 days, export 1 year).

Monitoring

  • Application Insights: requests, dependencies, exceptions, availability tests (every 5 min from 3 regions).
  • Custom metrics: cases.created, sla.breaches, outbox.pending, servicebus.dlq.
  • Azure Monitor alert rules → Action Group → ServiceNow + Teams channel (see Section 18).
  • Workbook “CaseFlow Operations” used daily by L2 and during hypercare.

Security architecture

  • Identity: Entra ID SSO, MFA, Conditional Access (compliant device or corporate IP); app roles + group assignment.
  • Authorisation: policy-based RBAC at API; resource rule “agents see only own team’s cases”; UI hides but never replaces API checks.
  • Network: private endpoints for SQL, Storage, Key Vault, Service Bus; App Service VNet integration; WAF on Application Gateway; NSGs.
  • Secrets: Key Vault only, accessed through managed identity; App Configuration holds Key Vault references. Nothing secret in code, pipeline variables or config files.
  • Data: TDE, TLS 1.2+, SQL Always Encrypted not required; attachments scanned (Defender for Storage + COMP-13) before download is allowed.
  • AppSec: parameterised queries, output encoding, CSP headers, anti-CSRF not needed for bearer-token SPA, dependency scanning, OWASP ZAP in pipeline, annual pen-test.
  • Compliance: UK-only data residency, 7-year retention, immutable history.

API conventions

  • Auth: Authorization: Bearer JWT; roles Agent, TeamLead, Supervisor, Compliance, Admin.
  • Headers: X-Correlation-Id (generated if missing), Idempotency-Key on POST, If-Match (ETag = RowVersion) on PUT.

  • Paging: pageSize (max 100) + cursor; response contains nextCursor.
  • Dates: ISO-8601 UTC. IDs: caseId (GUID) and human-readable caseNumber (CF-2026-000123).

Key design decisions

Two units, two purposes

  • Story points are a relative size (complexity + effort + uncertainty). The Product Owner uses them with velocity to forecast how many stories fit in a sprint. They are not hours and are never used to measure individuals.
  • Task hours are the developer’s bottom-up estimate, made in sprint planning to check the sprint is feasible against capacity. Remaining hours are updated daily.
  • Scale: Fibonacci 1, 2, 3, 5, 8, 13. A story > 8 points must be split before entering a sprint.
  • Component effort (Section 6) is in person-days; tasks in hours; epics in points + person-days. 1 person-day = 6 productive hours. For this team 1 story point ≈ 10.5 task hours (design, build, test, review, deploy). A 37 SP sprint therefore needs about 388 h, which fits inside the 396 h capacity.

Complexity, dependency, debt

  • Complexity is expressed in the points: 1–2 known pattern; 3–5 some design needed; 8 multiple components or integration; 13 = split. Examples: US-102 Search (8: indexes, paging, filters), US-304 CRM lookup (8: external system, resilience), US-101 Create case (5).
  • Dependency impact: stories with an external dependency (CRM sandbox D1, ERP contract D2, Entra groups D3) carry +20% task hours until a contract test passes. A late dependency moves the story to a later sprint; it does not inflate the estimate.
  • Technical debt: conscious shortcuts are logged as visible backlog items TD-01..TD-04 with their own points and are scheduled into Release 1.1/1.2 (10% of capacity is reserved for debt after go-live) so they do not silently erode the 198 SP scope.

Release pipeline (CD) — multi-stage YAML with environments

  1. DEV: Bicep what-if + deploy, DB bundle, API, Functions, SPA → smoke tests.

  4. PROD: approval by Release Manager after CAB approves the change record; Saturday window; DB restore point recorded; deploy to staging slot; smoke; slot swap; post-swap smoke; swap back if health check fails.

Configuration

  • Non-secret settings in Azure App Configuration with environment labels; feature flags (e.g. AutoAssign, ErpSync, DuplicateCheck).
  • Same package everywhere; behaviour differs only by configuration.
  • appsettings.json holds defaults only; no environment URLs or credentials.
  • Angular reads /assets/config.json at start-up so one build serves all environments.

Secrets

  • Secrets live in Key Vault per environment: crm-client-secret, erp-api-key, acs-connection.
  • App Service and Functions use managed identity with the Key Vault Secrets User role; App Config holds Key Vault references.
  • Pipeline uses a workload-identity service connection (OIDC), no stored passwords.
  • Expiry dates on every secret + Event Grid alert 30 days before (added after INC-1051 / CHG-2044).

Database deployment

  • Versioned migrations in source control; applied by the bundle under a deployment identity (db_ddladmin), never by the app login.
  • Expand → migrate → contract: schema changes are backward compatible, so the old version keeps working during slot swap and rollback.
  • Before PROD: restore-point marker + DBA script review; afterwards row-count and index checks.
  • Destructive changes (drop column) ship one version after the code stops using the column.

How Application Insights helps investigate

  1. Start with the symptom: Failures / Performance blade shows which operation is affected and since when; compare with the release time (deployment annotation).
  2. Take one failing request and open the end-to-end transaction view with its operation_Id / correlationId: Angular call → API → SQL → CRM → Service Bus → Function on one timeline.
  3. Find the slow or failing dependency (SQL, CRM, ERP). Duration and result code show whether it is our code or a partner.
  4. Read exceptions and traces (Serilog) for that operation: stack trace, handler name, parameters (no PII).
  5. Check scope: one user, one site or everyone? Use hashed user_AuthenticatedId, client_City, cloud_RoleInstance.
  6. Correlate with infrastructure: CPU, SQL Query Store, Service Bus metrics, Entra sign-in logs.
  7. Write the finding into the ticket: correlationId, KQL used, time window, hypothesis.

[HttpPost]
[Authorize(Policy = "CanCreateCase")]
public async Task<ActionResult<CaseDto>> Create(
    [FromBody] CreateCaseRequest request,
    [FromHeader(Name = "Idempotency-Key")] Guid idempotencyKey, CancellationToken ct)
{
    var result = await _mediator.Send(new CreateCaseCommand(request, idempotencyKey), ct);
    return result.Replayed ? Ok(result.Case)
                           : CreatedAtAction(nameof(GetById), new { id = result.Case.CaseId }, result.Case);
}

// CreateCaseHandler (Application layer, COMP-04)
public async Task<CreateCaseResult> Handle(CreateCaseCommand cmd, CancellationToken ct)
{
    var existing = await _cases.FindByClientRequestIdAsync(cmd.IdempotencyKey, ct);  // added for DEF-002
    if (existing is not null) return CreateCaseResult.Replay(existing);

    var customer = await _customers.GetAsync(cmd.Request.CustomerId, ct)
                   ?? throw new NotFoundException("Customer");

    if (!cmd.Request.ConfirmDuplicate && _flags.IsEnabled("DuplicateCheck") &&
        await _cases.HasOpenDuplicateAsync(customer.Id, cmd.Request.CategoryId, TimeSpan.FromHours(24), ct))
        throw new DuplicateCaseWarningException();                  // mapped to 409

    var dueAt = await _sla.GetDueAtAsync(cmd.Request.PriorityId, _clock.UtcNow, ct);
    var entity = Case.Create(_numbers.Next(), customer.Id, cmd.Request, dueAt, _user.Id, cmd.IdempotencyKey);

    await using var tx = await _uow.BeginAsync(ct);
    _cases.Add(entity);
    _history.Record(entity.Id, "CaseCreated", null, entity.Snapshot(), _user.Id);   // US-403
    _outbox.Add(new CaseCreated(entity.Id, entity.CaseNumber));                  // COMP-26
    try { await tx.CommitAsync(ct); }
    catch (DbUpdateException ex) when (ex.IsUniqueViolation("UX_Cases_ClientRequestId"))
    { return CreateCaseResult.Replay(await _cases.FindByClientRequestIdAsync(cmd.IdempotencyKey, ct)); }

    _telemetry.TrackEvent("CaseCreated", new { entity.CaseNumber });    // ALR-10 business signal
    return CreateCaseResult.Created(entity.ToDto());
}

The idempotency lines in this listing are the final v1.0.0 version; the first version of the handler (6 Mar) did not have them (see stages 15–16).

Root Cause (RCA)

PRB-0007 · completed Wed 27 May 2026

Five whys

  1. Why were creations slow? The duplicate-check SQL statement took 6 s.
  2. Why was it slow? It counted every open case of the customer using IX_Cases_CustomerId plus key lookups (140k reads) for accounts with thousands of cases.
  3. Why was that not seen earlier? Test data in QA/UAT averaged 3 cases per customer; production has 40 housing-association accounts with 500–3,000 cases each.
  4. Why did performance tests pass? The load test (Sprint 6) used the uniform data set; no skewed-data scenario existed (test design gap).
  5. Why did the code review not catch it? The LINQ Count() > 0 looked harmless and a suitable composite index was never designed (review checklist had no “existence check” item).

Trigger
