Part 1 — ASP.NET Core Web API fundamentals

What is ASP.NET Core Web API? Basic

ASP.NET Core Web API is Microsoft's cross-platform framework for building HTTP services that expose data and business operations to any client – browsers (SPA), mobile apps, other services, IoT devices. Instead of returning HTML pages, an API returns data (usually JSON) and uses HTTP itself (verbs, URLs, status codes, headers) as the contract.

Why does it exist?Modern systems are split: a React/Angular/mobile front end, several back-end services, third-party integrations. They all need one stable, language-neutral way to talk to the business logic. HTTP+JSON is that lingua franca, and Web API is the .NET toolkit that makes building it fast, testable and secure.

Key characteristics

  • Cross-platform & fast – runs on Windows, Linux, macOS, containers. Uses the Kestrel web server and consistently ranks at the top of TechEmpower benchmarks.
  • Unified framework – MVC and Web API were merged: both use the same ControllerBase, routing, model binding, filters and DI.
  • Built-in DI, configuration, logging – no third-party container needed.
  • Modular pipeline – behaviour is composed from small middleware components.
  • Two styles – Controller-based APIs (classes + attributes, covered here) and Minimal APIs (app.MapGet(...) lambdas). Same engine underneath.

REST architecture and RESTful principles Basic

REST (REpresentational State Transfer) is an architectural style defined by Roy Fielding (2000) – not a protocol or a standard. An API is "RESTful" when it follows a set of constraints that exploit how the web already works, so that clients and servers can evolve independently and scale.

Why constraints matterEach constraint buys a property: statelessness → horizontal scalability; uniform interface → any client can use any resource the same way; cacheability → performance; layered system → you can add load balancers/gateways transparently.

The six constraints

ConstraintMeaningIn ASP.NET Core
Client-ServerUI concerns separated from data storage concerns.SPA/mobile calls the API; API knows nothing about UI.
StatelessEach request carries all information needed; the server keeps no client session between requests.Send JWT in Authorization header on every call; no Session.
CacheableResponses declare whether they may be cached.Cache-Control, ETag, [ResponseCache], output caching.
Uniform interfaceResources identified by URIs; manipulated through representations; standard methods; self-descriptive messages; (HATEOAS).Nouns in URLs + HTTP verbs + Content-Type.
Layered systemClient can't tell if it talks to the end server or an intermediary.Reverse proxy / API gateway / CDN in front of Kestrel.
Code on demand (optional)Server may send executable code.Rarely used.

Stateless in practice

Common misconception"Stateless" does not mean "no data is stored". It means the server does not remember the client conversation. The database is state; an in-memory login session on one server is conversational state – and breaks when a load balancer sends the next request to another instance. That is why token-based auth (JWT) fits REST well.

Naming & design rules of thumb

  • Use plural nouns (/orders), lowercase, hyphens for multi-word (/order-items).
  • Nest only one level (/customers/7/orders); beyond that expose the child directly.
  • Use query strings for filtering, sorting and paging: ?status=open&sort=-date&page=2&pageSize=20.
  • Return the right status code and a consistent error body (ProblemDetails, RFC 9457).
  • Version your API from day one.

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{

    public ProductsController(IProductService svc) => _svc = svc;

    [HttpGet]
    public async Task<ActionResult<PagedResult<ProductDto>>> List([FromQuery] ProductQuery q, CancellationToken ct)
        => Ok(await _svc.SearchAsync(q, ct));

    // GET api/products/5
    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> Get(int id, CancellationToken ct)
    {
        var dto = await _svc.GetAsync(id, ct);
        return dto is null ? NotFound() : Ok(dto);
    }

    // POST api/products  -> 201 Created + Location: /api/products/{newId}
    [HttpPost]
    public async Task<ActionResult<ProductDto>> Create(CreateProductRequest req, CancellationToken ct)
    {
        var created = await _svc.CreateAsync(req, ct);
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created);
    }

    // PUT api/products/5  -> replaces everything; client must send the complete representation
    [HttpPut("{id:int}")]
    public async Task<IActionResult> Replace(int id, CreateProductRequest req, CancellationToken ct)
        => await _svc.ReplaceAsync(id, req, ct) ? NoContent() : NotFound();

    // PATCH api/products/5  -> only the supplied fields change (JSON Merge Patch style)
    [HttpPatch("{id:int}")]
    public async Task<IActionResult> Patch(int id, UpdateProductPartial req, CancellationToken ct)
        => await _svc.PatchAsync(id, req, ct) ? NoContent() : NotFound();

    // DELETE api/products/5  -> idempotent: second call may return 404 but the state is the same
    [HttpDelete("{id:int}")]
    public async Task<IActionResult> Delete(int id, CancellationToken ct)
        => await _svc.DeleteAsync(id, ct) ? NoContent() : NotFound();
}

PUT vs PATCH vs POST – the classic confusion

POST

Server decides the new id. Calling twice creates two resources. To make it retry-safe use an Idempotency-Key header.

PUT

Client sends the full object; missing fields are reset to default/null. Same call twice = same final state.

PATCH

Client sends only changes. Two formats: JSON Merge Patch (simple partial DTO) and JSON Patch (RFC 6902 operations, needs Microsoft.AspNetCore.JsonPatch).

[
  { "op": "replace", "path": "/price", "value": 79.9 },
  { "op": "add",     "path": "/tags/-", "value": "sale" },
  { "op": "remove",  "path": "/discontinuedReason" }
]
[HttpPatch("{id:int}")]
public async Task<IActionResult> JsonPatch(int id, [FromBody] JsonPatchDocument<ProductPatchModel> patch)
{
    var model = await _svc.GetPatchModelAsync(id);
    if (model is null) return NotFound();
    patch.ApplyTo(model, ModelState);                 // applies operations, records errors in ModelState
    if (!TryValidateModel(model)) return ValidationProblem(ModelState);
    await _svc.SavePatchAsync(id, model);
    return NoContent();
}

Controllers and API controllers Basic

A controller is a class whose public methods (actions) handle HTTP requests. Its single responsibility is HTTP translation: read the request (route, query, body, headers), call application logic, and turn the result into an HTTP response. Business rules belong in services.

ControllerBase vs Controller

  • ControllerBase – everything an API needs: Ok(), NotFound(), CreatedAtAction(), User, ModelState, HttpContext. Use this for APIs.
  • Controller – derives from ControllerBase and adds View support (Razor). Needed only for MVC apps that render HTML.

What [ApiController] gives you

The attribute enables opinionated API behaviours via conventions applied during startup – this is a favourite interview topic:

BehaviourWhat happens internally

Binding source inferenceComplex types → [FromBody]; simple types matching route tokens → [FromRoute]; others → [FromQuery]; IFormFile → [FromForm]; services → [FromServices].

[ApiController]
[Route("api/[controller]")]
[Produces("application/json")]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orders;
    private readonly ILogger<OrdersController> _log;

    public OrdersController(IOrderService orders, ILogger<OrdersController> log)
    {
        _orders = orders;      // injected by the DI container for each request
        _log = log;
    }

    [HttpGet("{id:guid}")]
    public async Task<ActionResult<OrderDto>> Get(Guid id)       // id inferred from route
    {
        _log.LogInformation("Fetching order {OrderId} for user {User}", id, User.Identity?.Name);
        var order = await _orders.GetAsync(id);
        return order is null ? NotFound() : order;                // implicit conversion to ActionResult<T>
    }

    [HttpPost]
    public async Task<ActionResult<OrderDto>> Place(PlaceOrderRequest req)   // req inferred [FromBody]
    {
        var order = await _orders.PlaceAsync(req);
        return CreatedAtAction(nameof(Get), new { id = order.Id }, order);
    }
}

Action return types

Specific type T

Simple, always 200. Can't return 404 without throwing.

IActionResult

Any result, but Swagger can't infer the body type – add [ProducesResponseType].

ActionResult<T> preferred

Either a T (200) or any ActionResult; type information flows into OpenAPI.

Keep controllers thinIf an action contains loops, calculations or database queries, move that to a service. A good action is 3-8 lines: bind → call → map to result.

Routing and attribute routing Basic

Routing maps an incoming URL + HTTP method to an executable endpoint (an action). ASP.NET Core uses endpoint routing in two phases:

  1. UseRouting() (implicit in .NET 6+) matches the request to an endpoint and stores it in HttpContext.
  2. Middleware between routing and the endpoint (CORS, auth, rate limiting) can now inspect endpoint metadata such as [Authorize].
  3. MapControllers() endpoints execute the matched action.

That metadata-aware design is why authorization middleware knows to challenge this endpoint but not /health.

DTOs (Data Transfer Objects) Basic

A DTO is a simple class/record shaped for the API contract, separate from your database entity. It carries data across the boundary between client and server.

Why not return entities?
  • Security: avoids leaking PasswordHash, internal flags; prevents over-posting.
  • Stability: DB schema changes shouldn't break clients.
  • Shape: flatten relations, add computed fields, hide navigation properties.
  • Serialization: avoids circular reference errors (Order → Customer → Orders...) and accidental lazy loading.

Dependency Injection (DI) Intermediate

Dependency Injection is a technique where a class receives the objects it depends on from the outside (usually via its constructor) instead of creating them with new. ASP.NET Core has a built-in IoC container (IServiceProvider) that builds the object graph for every request.

Why? Loose coupling (depend on IEmailSender, not SmtpEmailSender), testability (inject a fake), a single place to configure creation/lifetime, and automatic disposal of IDisposable services.

public class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> log, IHostEnvironment env) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var (status, title) = ex switch
        {
            NotFoundException        => (StatusCodes.Status404NotFound, "Resource not found"),
            ValidationException      => (StatusCodes.Status400BadRequest, "Validation failed"),
            ConflictException        => (StatusCodes.Status409Conflict, "Conflict"),
            UnauthorizedAccessException => (StatusCodes.Status403Forbidden, "Forbidden"),
            _                        => (StatusCodes.Status500InternalServerError, "An unexpected error occurred")
        };

        if (status >= 500) log.LogError(ex, "Unhandled exception {TraceId}", ctx.TraceIdentifier);
        else log.LogWarning("Handled {Type}: {Message}", ex.GetType().Name, ex.Message);

        ctx.Response.StatusCode = status;
        await ctx.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Status = status, Title = title,
            Detail = env.IsDevelopment() ? ex.ToString() : null,        // details only in Development
            Extensions = { ["traceId"] = ctx.TraceIdentifier }
        }, ct);
        return true;                                                    // handled: stop propagation
    }
}

Classic EF pitfalls
  • N+1 queries: lazy loading in a loop. Use .Include() or projection.
  • Tracking overhead: use AsNoTracking() for read endpoints.
  • Returning IQueryable from repositories leaks persistence details and defers execution unpredictably.
  • Sharing a DbContext across threads: it is not thread-safe – never Task.WhenAll two queries on the same instance.
  • Loading everything then filtering in memory: call ToList() only after Where/Select.

{

    public async Task ExecuteInTransactionAsync(Func<Task> work, CancellationToken ct = default)
    {

Asynchronous programming (async/await) Intermediate

A web server has a limited thread pool. Database calls, HTTP calls and file I/O spend most of their time waiting. With async/await, the thread is released back to the pool while the I/O is in flight, and a thread (any thread) resumes the method when the result arrives. Result: the same server handles far more concurrent requests.

Sync vs async request handling
Synchronous (blocking)
Thread 1: handles request A → blocked waiting for DB 200ms → continues
100 slow requests = 100 blocked threads → thread-pool starvation, 503s
Asynchronous
Thread 1: starts request A → await DB → returns to pool
Thread 1 serves request B meanwhile; any free thread resumes A when DB responds

Part 2 — Authentication & authorization

Authentication vs authorization: the big picture Basic

Authentication (AuthN) – "Who are you?"

Verifying identity from credentials (password, token, certificate). Output: a ClaimsPrincipal attached to HttpContext.User. Failure → 401.

Authorization (AuthZ) – "What may you do?"

Deciding whether that identity may perform this operation (roles, claims, policies, resource ownership). Failure → 403.

How ASP.NET Core models security internally

  • Claim – a statement about a subject: (type="role", value="Admin"), ("email", "a@b.com").
  • ClaimsIdentity – a set of claims issued by one authority, plus the authentication type ("Bearer", "Cookies").
  • ClaimsPrincipal – the user: one or more identities. This is HttpContext.User / User in controllers.
  • Authentication scheme – a named configuration (handler + options): JwtBearerDefaults.AuthenticationScheme = "Bearer". An app can register several.
  • Authentication handler – code implementing AuthenticateAsync (read the credential and build the principal), ChallengeAsync (respond 401 / redirect to login) and ForbidAsync (403).

Basic Authentication Basic

What it is and why

The oldest HTTP scheme (RFC 7617). The client sends Authorization: Basic base64(username:password) on every request. It exists because it is trivial to implement and supported by every HTTP client and tool. It is not encryption – Base64 is reversible, so it must only ever be used over HTTPS.

Flow

How credentials are encoded and validated

echo -n "alice:P@ssw0rd" | base64        # YWxpY2U6UEBzc3cwcmQ=
curl -u alice:P@ssw0rd https://localhost:7001/api/reports     # curl builds the header for you

The server splits at the first colon, then looks the user up and compares the password against a salted hash (never plain text) in constant time.

ASP.NET Core implementation

There is no built-in Basic handler, so you write an AuthenticationHandler<T>. This also teaches how every scheme works internally.

public class BasicAuthenticationHandler : AuthenticationHandler<AuthenticationSchemeOptions>
{
    private readonly IUserValidator _users;
    public BasicAuthenticationHandler(IOptionsMonitor<AuthenticationSchemeOptions> options, ILoggerFactory logger,
        UrlEncoder encoder, IUserValidator users) : base(options, logger, encoder) => _users = users;

    protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        if (!Request.Headers.TryGetValue("Authorization", out var header))
            return AuthenticateResult.NoResult();                       // no credentials: let [AllowAnonymous] pass / challenge later

        if (!AuthenticationHeaderValue.TryParse(header, out var auth) || !"Basic".Equals(auth.Scheme, StringComparison.OrdinalIgnoreCase) || auth.Parameter is null)
            return AuthenticateResult.Fail("Invalid Authorization header");

        string[] parts;
        try { parts = Encoding.UTF8.GetString(Convert.FromBase64String(auth.Parameter)).Split(':', 2); }
        catch (FormatException) { return AuthenticateResult.Fail("Invalid Base64"); }
        if (parts.Length != 2) return AuthenticateResult.Fail("Invalid credentials format");

        var user = await _users.ValidateAsync(parts[0], parts[1]);      // hash check inside
        if (user is null) return AuthenticateResult.Fail("Invalid username or password");

        var claims = new[] { new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()), new Claim(ClaimTypes.Name, user.UserName), new Claim(ClaimTypes.Role, user.Role) };
        var principal = new ClaimsPrincipal(new ClaimsIdentity(claims, Scheme.Name));
        return AuthenticateResult.Success(new AuthenticationTicket(principal, Scheme.Name));
    }

    protected override Task HandleChallengeAsync(AuthenticationProperties props)
    {
        Response.Headers.WWWAuthenticate = "Basic realm=\"DemoShop API\", charset=\"UTF-8\"";   // tells browsers/clients to prompt
        return base.HandleChallengeAsync(props);                                                 // sets 401
    }
}

Cookie-Based Authentication Basic

What it is and why

After a successful login the server creates an encrypted, signed authentication ticket (the serialized ClaimsPrincipal) and returns it in a Set-Cookie header. The browser automatically attaches the cookie to every subsequent request to that site. It exists because browsers have a built-in, secure storage and transmission mechanism for it – JavaScript doesn't need to handle credentials at all.

How the cookie is generated and validated

ASP.NET Core serializes the principal, encrypts and signs it with keys managed by the Data Protection system, and puts the result in the cookie. On each request the cookie handler decrypts it, checks signature + expiry (and optional sliding renewal) and rebuilds User. No server-side session store is required – but in a web farm every instance must share the same Data Protection keys.

JWT (JSON Web Token) Authentication Intermediate

What it is and why it is required

A JWT (RFC 7519) is a compact, URL-safe, signed string carrying claims. Because the signature lets any server verify it using only a key, the API needs no session lookup – this is what makes token auth stateless and horizontally scalable, and why it dominates SPA/mobile/microservice security.

Anatomy

header.payload.signature

1. Header

{ "alg": "HS256", "typ": "JWT" }

Algorithm and token type. Base64Url encoded.

2. Payload (claims)

{ "sub": "42", "name": "Alice",
  "role": "Admin",
  "iss": "https://api.shop",
  "aud": "shop-clients",
  "iat": 1735689600,
  "exp": 1735690500 }

Registered claims (iss, sub, aud, exp, nbf, iat, jti) + custom claims. Readable by anyone – not encrypted!

3. Signature

HMACSHA256(
  base64Url(header) + "." +
  base64Url(payload),
  secretKey)

Proves integrity & origin. Change one byte of the payload and verification fails.

Signing algorithms

AlgorithmTypeKeyUse when
HS256Symmetric (HMAC)One shared secret signs and verifiesSingle API that issues and validates its own tokens
RS256 / ES256AsymmetricPrivate key signs; public key verifiesA separate identity provider issues tokens; many APIs only verify (Entra ID, Auth0, Keycloak publish a JWKS endpoint)

Refresh Token Mechanism Advanced

What it is and why

A short-lived access token limits the damage of theft, but forcing users to log in every 15 minutes is unusable. A refresh token is a long-lived, opaque, server-tracked credential whose only power is to obtain a new access token. Because it is stored server-side it can be revoked, giving you the benefits of both stateless access tokens and revocable sessions.

public class RefreshToken
{
    public int Id { get; set; }
    public int UserId { get; set; }
    public User User { get; set; } = null!;
    public string TokenHash { get; set; } = "";       // store a SHA-256 hash, never the raw token (like a password)
    public DateTime CreatedAt { get; set; }
    public DateTime ExpiresAt { get; set; }
    public string CreatedByIp { get; set; } = "";
    public DateTime? RevokedAt { get; set; }
    public DateTime? UsedAt { get; set; }              // rotation: each refresh token is single-use
    public string? ReplacedByHash { get; set; }
    public bool IsActive => RevokedAt is null && UsedAt is null && DateTime.UtcNow < ExpiresAt;
}
public static string NewRawToken() => Convert.ToBase64String(RandomNumberGenerator.GetBytes(64));
public static string Hash(string raw) => Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(raw)));

public async Task<TokenResponse?> RefreshAsync(string rawToken, string ip, CancellationToken ct)
{
    var hash = Hash(rawToken);
    var stored = await _db.RefreshTokens.Include(r => r.User).SingleOrDefaultAsync(r => r.TokenHash == hash, ct);
    if (stored is null) return null;                                   // unknown token => 401

    if (stored.UsedAt is not null || stored.RevokedAt is not null)
    {   // A rotated/revoked token came back: either a replay attack or a stolen copy => kill every session of the user
        await _db.RefreshTokens.Where(r => r.UserId == stored.UserId && r.RevokedAt == null)
                               .ExecuteUpdateAsync(s => s.SetProperty(r => r.RevokedAt, DateTime.UtcNow), ct);
        _log.LogWarning("Refresh token reuse detected for user {UserId}", stored.UserId);
        return null;
    }
    if (DateTime.UtcNow >= stored.ExpiresAt) return null;

    var raw = NewRawToken();
    stored.UsedAt = DateTime.UtcNow;                                   // rotation: old token is now dead
    stored.ReplacedByHash = Hash(raw);
    _db.RefreshTokens.Add(new RefreshToken
    {
        UserId = stored.UserId, TokenHash = Hash(raw), CreatedAt = DateTime.UtcNow, CreatedByIp = ip,
        ExpiresAt = DateTime.UtcNow.AddDays(_jwt.RefreshTokenDays)
    });
    await _db.SaveChangesAsync(ct);
    return new TokenResponse(_tokens.CreateAccessToken(stored.User), raw, "Bearer", _jwt.AccessTokenMinutes * 60);
}
async function api(url: string, init: RequestInit = {}, retry = true): Promise<Response> {
  const res = await fetch(url, { ...init, headers: { ...init.headers, Authorization: `Bearer ${auth.accessToken}` } });
  if (res.status === 401 && retry) {
    const ok = await auth.refresh();               // POST /api/auth/refresh with the stored refresh token (single in-flight promise!)
    if (ok) return api(url, init, false);          // retry exactly once
    auth.logout();                                 // refresh failed => back to login
  }
  return res;
}
Best practices
  • Rotate on every use; detect reuse; store only hashes.
  • Browser: keep the refresh token in an HttpOnly; Secure; SameSite cookie scoped to /api/auth, not in localStorage.
  • Cap total session length (absolute expiry) and revoke on password change/logout.
  • Run a background cleanup of expired tokens.

OAuth 2.0 Advanced

What it is and why

OAuth 2.0 (RFC 6749) is an authorization framework, not an authentication protocol. It lets an application obtain limited access to a resource on behalf of a user (or itself) without ever seeing the user's password. Example: "Allow ExpenseApp to read your calendar" – ExpenseApp gets a token with the scope calendar.read, not your Google password.

Roles

The user who owns the data.

Client

The application requesting access (SPA, mobile, web app, service).

Authorization Server

Authenticates the user, obtains consent, issues tokens (Entra ID, Auth0, Keycloak, Duende IdentityServer).

Resource Server

Your Web API; accepts and validates access tokens.

A public client (SPA/mobile) cannot keep a client secret. If an attacker intercepts the authorization code they could redeem it. PKCE binds the code to a random code_verifier that only the genuine client knows, so a stolen code is useless.

API Key Authentication Basic

What it is and why

An API key is a long random string that identifies the calling application (not a person). The client sends it in a header (conventionally X-Api-Key). It exists to give partners/integrations simple, revocable, per-client access that can be rate-limited, billed and audited.

public class ApiKeyHandler(IOptionsMonitor<AuthenticationSchemeOptions> o, ILoggerFactory l, UrlEncoder e, IApiKeyStore store)
    : AuthenticationHandler<AuthenticationSchemeOptions>(o, l, e)
{
    public const string Scheme = "ApiKey";
    protected override async Task<AuthenticateResult> HandleAuthenticateAsync()
    {
        if (!Request.Headers.TryGetValue("X-Api-Key", out var provided) || string.IsNullOrWhiteSpace(provided))
            return AuthenticateResult.NoResult();

        var hash = Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(provided.ToString())));
        var client = await store.FindByHashAsync(hash);                 // keys stored hashed, like passwords

        var claims = new List<Claim> { new(ClaimTypes.NameIdentifier, client.Id.ToString()), new(ClaimTypes.Name, client.Name), new("client_type", "partner") };
        claims.AddRange(client.Scopes.Select(s => new Claim("scope", s)));
        return AuthenticateResult.Success(new AuthenticationTicket(new ClaimsPrincipal(new ClaimsIdentity(claims, Scheme)), Scheme));
    }
}

Claims-Based Authorization Intermediate

A claim is a name/value fact about the user (department=Finance, subscription=Premium, age=34, permission=orders.refund). Claims-based authorization checks those facts instead of (or in addition to) roles, which makes decisions finer grained and data-driven. Roles are simply one kind of claim.

public class PermissionClaimsTransformation(AppDbContext db) : IClaimsTransformation
{
    public async Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal)
    {
        if (principal.Identity is not ClaimsIdentity id || id.HasClaim(c => c.Type == "permission")) return principal;   // idempotent!
        var userId = int.Parse(principal.FindFirstValue("sub")!);
        var perms = await db.UserPermissions.Where(p => p.UserId == userId).Select(p => p.Name).ToListAsync();
        foreach (var p in perms) id.AddClaim(new Claim("permission", p));
        return principal;
    }
}

public record MinimumAgeRequirement(int Age) : IAuthorizationRequirement;

public class MinimumAgeHandler : AuthorizationHandler<MinimumAgeRequirement>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, MinimumAgeRequirement req)
    {
        var dob = ctx.User.FindFirst("date_of_birth")?.Value;
        if (DateTime.TryParse(dob, out var d) && d.AddYears(req.Age) <= DateTime.Today)
            ctx.Succeed(req);                         // not calling Succeed => requirement is not met (others may still satisfy it)
        return Task.CompletedTask;
    }
}

Part 3 — Swagger & OpenAPI

What are Swagger and OpenAPI? Basic

The problem they solveAn API without a machine-readable contract forces every consumer to read prose docs, guess payload shapes and hand-write HTTP code. Docs drift out of date and clients break silently. A formal, machine-readable description lets tools generate documentation, test UIs, client SDKs, mocks and contract tests from a single source of truth.

OpenAPI

The OpenAPI Specification (OAS) is a vendor-neutral, language-agnostic standard (governed by the OpenAPI Initiative / Linux Foundation) for describing HTTP APIs in JSON or YAML: paths, operations, parameters, request bodies, responses, schemas, security schemes. Current versions: 3.0.x and 3.1.

Swagger

Swagger was the original name of the specification (v1.2, 2.0). In 2015 the spec was donated and renamed OpenAPI. "Swagger" now refers to the tooling from SmartBear: Swagger UI, Swagger Editor, Swagger Codegen. In .NET, Swashbuckle.AspNetCore (and NSwag) generate an OpenAPI document and host Swagger UI.

How Swagger discovers your endpoints

  1. At startup ASP.NET Core registers every action as an endpoint with metadata (route pattern, HTTP method, parameter descriptors, [ProducesResponseType], [Authorize], [Consumes]...).
  2. The framework's API Explorer (IApiDescriptionGroupCollectionProvider, enabled by AddEndpointsApiExplorer() / AddControllers()) converts that metadata into ApiDescription objects – a neutral description of each operation.
  3. On request to /swagger/v1/swagger.json, Swashbuckle's ISwaggerProvider loops over the ApiDescriptions, builds paths, generates a JSON Schema for every parameter/DTO type via ISchemaGenerator (reflection over properties, attributes like [Required], [Range]), then runs filters (operation/schema/document filters) you registered.
  4. The result is serialized as the OpenAPI JSON. No separate documentation code is written – reflection plus attributes is the source.
Swagger UI runs in your browser and the "Execute" button issues a real fetch to your API. That is why you need CORS correctness only when the UI is hosted on a different origin, and why the Authorize button just adds an Authorization header to those requests.

Enabling JWT Bearer authentication in Swagger UI and testing endpoints Intermediate

Swagger UI sends requests from your browser, so to test a protected endpoint it needs a way to attach the token. The security scheme from the previous chapter creates the Authorize button.

What each part of the configuration means

  • SecuritySchemeType.Http + Scheme = "bearer" → Swagger UI shows a single "Value" box and automatically prefixes Bearer . (If you use SecuritySchemeType.ApiKey instead, users must type "Bearer eyJ..." manually.)
  • AddSecurityDefinition → declares what authentication exists (goes to components.securitySchemes).
  • OperationFilter/AddSecurityRequirement → declares which operations use it (security on each operation); also decides where padlocks appear.

Testing workflow

  1. Run the API (dotnet run) and open https://localhost:7001/swagger.
  2. Try a protected endpoint (e.g. GET /api/products) before authorizing → 401 Unauthorized. This proves security works.
  3. Expand POST /api/auth/login (unsecured, no padlock) → Try it out → Execute with valid credentials → copy accessToken from the response body.
  4. Click Authorize (top right), paste only the token, click Authorize, Close. Padlocks become closed.
  5. Call GET /api/products again → 200 OK. The curl shown contains -H 'Authorization: Bearer ...'.
  6. Call DELETE /api/products/1 with a normal user's token → 403 Forbidden; with the admin token → 204 No Content.
  7. Wait for the token to expire (or let the Token-Expired header appear) → 401 → call /refresh, authorize again with the new token.
Common problems
  • Still 401 after authorizing: you pasted "Bearer " too (double prefix), token expired, wrong issuer/audience/key between the issuing code and validation code, or UseAuthentication() is missing / placed after UseAuthorization().
  • No padlock: operation filter doesn't see [Authorize] (e.g. policy applied via RequireAuthorization() on a minimal API – check EndpointMetadata).
  • Swagger exposed in production: enable it only for Development/Staging or protect the route.

What gets generated?

  • Models – one class/interface per schema (ProductDto, CreateProductRequest).
  • Client / service – one method per operation: builds the URL, serializes the body, adds headers, sends the HTTP request, deserializes the response, throws a typed exception on error status codes.
  • Interfaces (IProductsClient) – for DI and mocking in tests.
  • Optional server stubs (controller base classes/interfaces) when doing contract-first development.
Code-first vs contract-first Code-first (this guide): write controllers → generate the spec → generate clients. Contract-first: write/agree the OpenAPI document first → generate server stubs and clients in parallel.

Rules for happy generated clients
  • Never hand-edit generated files – wrap them, or customize templates / partial classes.
  • Give operations stable operationIds and tags, otherwise method names change when you refactor.
  • Declare every response with [ProducesResponseType]; use enums as strings (JsonStringEnumConverter + c.UseInlineDefinitionsForEnums() if needed).
  • Mark non-nullable properties required and enable nullable reference types so generated types aren't all | undefined.
  • Don't generate clients from a Swagger doc that exposes internal/admin endpoints to external consumers – split documents per audience.

Benefits

  • No hand-written HTTP/serialization code
  • Compile-time contract checking
  • Faster onboarding, consistent behaviour
  • Docs, tests and clients share one source of truth

Trade-offs

  • Generated code can be verbose or opinionated
  • Quality depends on the quality of the spec
  • Pipeline step to maintain
  • Tool version upgrades change output

Step 7 – AuthService (registration, login, refresh)

public class AuthService(AppDbContext db, IPasswordHasher<User> hasher, ITokenService tokens, IOptions<JwtOptions> jwt, ILogger<AuthService> log) : IAuthService
{
    public static string Hash(string raw) => Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(raw)));

    public async Task<UserDto> RegisterAsync(RegisterRequest r, CancellationToken ct)
    {
        var email = r.Email.Trim().ToLowerInvariant();
        if (await db.Users.AnyAsync(u => u.Email == email, ct)) throw new ConflictException("A user with this e-mail already exists.");

        var user = new User { Email = email, FullName = r.FullName.Trim(), Role = "User" };   // role is NEVER taken from the request (prevents privilege escalation)
        user.PasswordHash = hasher.HashPassword(user, r.Password);
        db.Users.Add(user);
        await db.SaveChangesAsync(ct);
        return new UserDto(user.Id, user.Email, user.FullName, user.Role);
    }

    public async Task<TokenResponse?> LoginAsync(LoginRequest r, string ip, CancellationToken ct)
    {
        var user = await db.Users.SingleOrDefaultAsync(u => u.Email == r.Email.ToLower(), ct);
        var ok = user is not null && hasher.VerifyHashedPassword(user, user.PasswordHash, r.Password) != PasswordVerificationResult.Failed;
        if (!ok) { log.LogWarning("Failed login for {Email} from {Ip}", r.Email, ip); return null; }   // same result for unknown user and wrong password

        return await IssueAsync(user!, ip, ct);
    }

    public async Task<TokenResponse?> RefreshAsync(string raw, string ip, CancellationToken ct) { /* see Refresh Token chapter: lookup hash, detect reuse, rotate */ }

    private async Task<TokenResponse> IssueAsync(User user, string ip, CancellationToken ct)
    {
        var rt = tokens.CreateRefreshToken(user, ip, out var raw);
        db.RefreshTokens.Add(rt);
        await db.SaveChangesAsync(ct);
        return new TokenResponse(tokens.CreateAccessToken(user), raw, "Bearer", jwt.Value.AccessTokenMinutes * 60);
    }
}

public class ProductService(AppDbContext db) : IProductService

    public async Task<PagedResult<ProductDto>> SearchAsync(ProductQuery q, CancellationToken ct)
    {
        var query = db.Products.AsNoTracking();
        if (!string.IsNullOrWhiteSpace(q.Search)) query = query.Where(p => p.Name.Contains(q.Search));
        var total = await query.CountAsync(ct);
        var items = await query.OrderBy(p => p.Id).Skip((q.Page - 1) * q.PageSize).Take(q.PageSize)
                               .Select(p => new ProductDto(p.Id, p.Name, p.Price, p.Stock)).ToListAsync(ct);
        return new(q.Page, q.PageSize, total, items);
    }

    public async Task<ProductDto?> GetAsync(int id, CancellationToken ct) => (await db.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct)) is { } p ? ToDto(p) : null;

    public async Task<ProductDto> CreateAsync(CreateProductRequest r, CancellationToken ct)
    {
        var p = new Product { Name = r.Name.Trim(), Price = r.Price, Stock = r.Stock };
        db.Products.Add(p); await db.SaveChangesAsync(ct); return ToDto(p);
    }

    public async Task<bool> ReplaceAsync(int id, CreateProductRequest r, CancellationToken ct)
    {
        var p = await db.Products.FindAsync(new object[] { id }, ct); if (p is null) return false;
        (p.Name, p.Price, p.Stock) = (r.Name.Trim(), r.Price, r.Stock);
        await db.SaveChangesAsync(ct); return true;
    }

    public async Task<bool> DeleteAsync(int id, CancellationToken ct) => await db.Products.Where(p => p.Id == id).ExecuteDeleteAsync(ct) > 0;

Part 7 — Interview preparation & additional resources

Common ASP.NET Core Web API interview questions Prep

Filter by topic, then expand a question and try to answer it aloud before reading the answer.

What is the difference between ASP.NET Web API (.NET Framework) and ASP.NET Core Web API? core

Core is cross-platform, modular, faster (Kestrel), has built-in DI, unified MVC + Web API controllers (ControllerBase), configuration via providers (no Web.config), a middleware pipeline instead of HTTP modules/handlers, and ships as NuGet packages with side-by-side versioning. Classic Web API was Windows/IIS-bound with System.Web.

Explain the request pipeline and why middleware order matters. core

Each middleware receives the context and calls next or short-circuits; code after await next() runs on the way back. Order determines behaviour: exception handler first (wraps everything), CORS before auth (pre-flight has no credentials), UseAuthentication before UseAuthorization (identity must exist before it is checked), rate limiter/static files placement affects what they can short-circuit. Wrong order causes classic bugs such as CORS errors that are really 401s.

Transient vs Scoped vs Singleton – and what is a captive dependency? core

Transient: new instance every resolution; Scoped: one per request/scope; Singleton: one per app. A captive dependency is a longer-lived service holding a shorter-lived one (singleton → scoped DbContext), which makes the scoped instance live forever and not thread-safe. Fix by injecting IServiceScopeFactory or aligning lifetimes. ValidateScopes catches this in Development.

Middleware vs filters: when would you use each? core

Middleware runs for every request and is unaware of MVC (no model state, action args). Filters run inside the MVC action pipeline with access to action context, arguments and results. Use middleware for cross-cutting HTTP concerns (logging, CORS, exception handling, auth); filters for action-level concerns (audit of arguments, custom validation, result shaping). Authorization policies are enforced by middleware using endpoint metadata.

What does [ApiController] do? core

Enables automatic 400 responses for invalid ModelState, binding-source inference ([FromBody] for complex types, etc.), ProblemDetails for error status codes, requires attribute routing and multipart inference. It's implemented through MVC conventions/filters (ModelStateInvalidFilter) and can be tuned via ApiBehaviorOptions.

IOptions vs IOptionsSnapshot vs IOptionsMonitor? core

IOptions: singleton, read once. IOptionsSnapshot: scoped, re-read per request (no singleton injection). IOptionsMonitor: singleton with OnChange notifications and current value. Combine with ValidateOnStart() to fail fast on bad config.

How do you handle exceptions globally? core

Use UseExceptionHandler with an IExceptionHandler (.NET 8) that maps exception types to status codes and writes ProblemDetails, log once with a trace id, hide details outside Development. Avoid try/catch in each action. Alternative: an exception filter (only covers MVC) or custom middleware.

PUT vs PATCH vs POST? What does idempotent mean? rest

POST creates / triggers actions (not idempotent: two calls = two resources). PUT replaces the whole resource at a known URI (idempotent). PATCH partially updates (idempotent only if the patch semantics are). Idempotent: repeating the request leaves the server in the same state, which makes retries safe. Add an Idempotency-Key header to make POST retry-safe.

401 vs 403? 400 vs 422? 404 vs 204? rest

401: not authenticated (or invalid/expired token) – client should authenticate. 403: authenticated but lacks permission – re-login doesn't help. 400: malformed or invalid request; 422: syntactically valid but semantically wrong (many APIs use 400 + ValidationProblemDetails for both). 404: resource doesn't exist; 204: success with intentionally empty body (PUT/DELETE).

What makes an API RESTful? rest

Client-server, stateless, cacheable, uniform interface (resource URIs, standard verbs, representations, HATEOAS), layered system. In practice: nouns in URLs, correct verbs/status codes, statelessness (tokens not sessions), consistent errors, versioning, pagination, caching headers.

How do you implement pagination, filtering and sorting? rest

Query string parameters bound to a query object ([FromQuery] ProductQuery) with validated ranges (max page size!). Offset paging (Skip/Take) is simple but slow on deep pages; keyset/cursor paging (WHERE Id > @last ORDER BY Id) scales better. Return metadata (total, page) in the body or headers; always have a deterministic OrderBy.

How does JWT authentication work in ASP.NET Core, step by step? auth

Login endpoint verifies credentials, creates a JwtSecurityToken with claims, issuer, audience, expiry, signed with a key; the client sends it as Authorization: Bearer. JwtBearerHandler reads the header, validates signature/issuer/audience/lifetime using TokenValidationParameters, builds a ClaimsPrincipal and assigns HttpContext.User. Then UseAuthorization evaluates [Authorize] metadata: not authenticated → 401, policy fails → 403.

Where should a SPA store the JWT? auth

Trade-off: localStorage is readable by any XSS script; HttpOnly cookies are immune to JS theft but need CSRF protection (SameSite, anti-forgery). Best practice: short-lived access token in memory, refresh token in an HttpOnly, Secure, SameSite cookie scoped to the refresh endpoint, or use the BFF pattern so tokens never reach the browser.

How do you revoke a JWT? auth

You can't invalidate a stateless token before expiry without state. Options: keep access tokens very short-lived and revoke refresh tokens; maintain a deny-list of jti (cache with TTL = remaining lifetime); include a token version/security stamp claim checked against the DB on sensitive endpoints (OnTokenValidated); rotate signing keys in emergencies.

OAuth 2.0 vs OpenID Connect vs JWT? auth

OAuth 2.0 = delegated authorization framework (access tokens, scopes, flows). OIDC = identity layer on OAuth 2.0 adding ID token, userinfo and discovery (authentication/SSO). JWT = a token format, usable for access tokens and ID tokens. They are complementary, not alternatives.

Explain refresh token rotation and reuse detection. auth

Each refresh yields a new refresh token and invalidates the old one. If an old (used) token is presented again, either the client or an attacker has a stale copy, so the server revokes the whole token family/user sessions, forcing re-login. Store only hashes, keep absolute session limits, and bind tokens to device/IP if appropriate.

Role-based vs claims-based vs policy-based vs resource-based authorization? auth

Roles are a special claim, coarse grained. Claims check attributes/permissions. Policies compose requirements with handlers (any logic, DI-enabled). Resource-based uses IAuthorizationService.AuthorizeAsync(user, resource, requirement) to decide per object (ownership). Everything is evaluated by the policy engine.

How do you protect against CSRF, XSS, SQL injection and over-posting in a Web API? auth

CSRF: not exposed when auth is a bearer header; with cookies use SameSite + anti-forgery tokens. XSS: encode output, CSP, HttpOnly cookies, don't store tokens in localStorage. SQL injection: EF Core/parameterised queries only (FromSqlInterpolated, never string concat). Over-posting: bind to request DTOs, never entities; never accept role/ids you control.

How is a password stored securely? auth

Never plain text or fast hashes. Use a slow, salted, adaptive KDF: ASP.NET Core Identity's PasswordHasher (PBKDF2, per-user salt, iteration count embedded), or bcrypt/Argon2. Verify in constant time, add lockout/rate limiting, return identical errors for unknown user vs wrong password.

What is the N+1 problem in EF Core and how do you fix it? data

Loading a list then touching a navigation property per item triggers one query per item. Fix with Include/ThenInclude, projection (Select to DTO), split queries (AsSplitQuery) for large collections, and disabling lazy loading proxies. Verify via logging the generated SQL.

Tracking vs no-tracking queries; AsNoTracking? data

Tracked entities are snapshotted so SaveChanges can detect changes; costly in memory/CPU. For read-only endpoints use AsNoTracking() (or projection which is never tracked). Use tracking only when you'll modify and save.

How do you handle concurrency conflicts? data

Optimistic concurrency with a [Timestamp]/rowversion or [ConcurrencyCheck] column: EF adds it to the WHERE of UPDATE/DELETE; if no row matches it throws DbUpdateConcurrencyException. Return 409 (or 412 with ETag/If-Match) and let the client reload and retry.

Is the Repository pattern still needed with EF Core? data

DbContext already is a unit of work and DbSet a repository. A generic wrapper often adds indirection and hides features. Use repositories/specifications for aggregate-focused domains, to isolate persistence for testing or multi-store scenarios; otherwise use DbContext in query/command handlers and test with SQLite in-memory or Testcontainers.

What is the difference between Swagger and OpenAPI? swagger

OpenAPI is the specification (formerly the Swagger Specification). Swagger is the SmartBear tooling around it (UI, Editor, Codegen). Swashbuckle/NSwag generate the OpenAPI document; Swagger UI renders it.

How does Swashbuckle discover endpoints and build the schema? swagger

From ASP.NET Core's API Explorer (ApiDescriptions derived from endpoint metadata) and reflection over DTO types (JSON-schema generation honouring DataAnnotations, XML comments, [ProducesResponseType]), then operation/schema/document filters customise the result.

How do you add JWT support to Swagger UI? swagger

AddSecurityDefinition("Bearer", new OpenApiSecurityScheme { Type = Http, Scheme = "bearer", BearerFormat = "JWT" }) and an AddSecurityRequirement or an operation filter that adds the requirement to [Authorize] actions. The Authorize button then sends Authorization: Bearer <token> with Try-it-out requests.

Why generate API clients, and how do you keep them in sync? swagger

Removes hand-written HTTP/serialization code and gives compile-time contract checks. Export the spec in CI, diff for breaking changes, regenerate clients in the consumer pipeline (NSwag/OpenAPI Generator), never edit generated code, use stable operation ids and declare all responses.

How would you make an API faster? perf

Async I/O, AsNoTracking + projection + indexes, paging, response compression, output/memory/distributed caching with proper invalidation, HTTP/2, connection pooling (IHttpClientFactory, AddDbContextPool), avoid large payloads and serialization overhead (source-generated System.Text.Json), reduce allocations, measure with benchmarks/APM before optimising.

What is thread pool starvation and how does it relate to async? perf

Blocking calls (.Result, .Wait(), sync I/O) hold threads while idle; under load the pool can't supply threads fast enough, causing latency spikes and timeouts. Using async/await end to end releases threads during I/O so a small pool serves many requests.

How do you scale a stateless API horizontally? perf

Keep nothing in process that must be shared: tokens instead of sessions, distributed cache (Redis) instead of IMemoryCache for shared data, shared Data Protection keys, centralised rate limits at the gateway, health checks + load balancer, idempotent operations and background work via queues.

Design: a mobile app needs login, token refresh and offline-safe retries. What do you build? design

OIDC/JWT with short access tokens + rotating refresh tokens stored in the platform secure store; an HTTP interceptor that refreshes once on 401 (single in-flight refresh); idempotency keys on POSTs; exponential-backoff retry via Polly for transient errors only; ETag/If-Match for conflicting updates; versioned API and server-driven deprecation headers.

Design: two microservices need to call each other securely. design

OAuth2 client-credentials against a central IdP (Entra ID, Keycloak): each service has its own client id/secret or certificate, requests tokens with narrow scopes/app roles, caches them until near expiry, and the target API validates audience + scope via JwtBearer. Add mTLS or a service mesh for transport identity.

How do you version and deprecate an API without breaking clients? design

Additive changes are non-breaking. For breaking changes introduce a new version (URL or header), keep the old one with Deprecated = true, emit Sunset/Deprecation headers, publish migration notes, track usage per version in telemetry, and remove it only after the sunset date.

Frequently asked technical questions FAQ

Short, practical answers to the questions developers search for most often while building Web APIs.

Why do I get a CORS error when the real problem is a 401 or 500?

The browser hides the real response when CORS headers are missing. A failing pre-flight (OPTIONS), an exception thrown before UseCors runs, or a 401 returned before the CORS middleware all look like "CORS policy" errors in the console. Put UseCors early (after UseRouting, before UseAuthentication), and check the Network tab / curl to see the actual status.

Why is my [Authorize] endpoint returning 401 even with a valid-looking token?
  • Missing Bearer prefix or the token has extra quotes/whitespace.
  • Issuer, Audience or signing key in TokenValidationParameters differ from the ones used when the token was created.
  • Token expired (ClockSkew defaults to 5 minutes, so expiry is slightly lenient).
  • UseAuthentication() is missing or placed after UseAuthorization().
  • The default scheme is not JWT (e.g. Identity cookies registered after AddJwtBearer). Pass AuthenticationSchemes or set the defaults.
  • Read the WWW-Authenticate response header: it states invalid_token, The audience is invalid, The token expired at ....
Why are my claim types different (sub becomes nameidentifier)?

The legacy JwtSecurityTokenHandler maps short JWT claim names to long WS-* URIs. Set options.MapInboundClaims = false (or clear JwtSecurityTokenHandler.DefaultInboundClaimTypeMap) and configure NameClaimType/RoleClaimType so User.Identity.Name and IsInRole keep working.

Should I return entities or DTOs?

DTOs. Entities leak columns (password hashes), expose navigation cycles (JSON serializer loops), couple the contract to the database schema, and enable over-posting. Map with a manual mapper, Mapperly (source generated) or AutoMapper; use projection (Select) so EF only loads needed columns.

How do I return a different status code for "not found" vs "no results"?

A single resource lookup (GET /products/42) that does not exist is 404. A collection query (GET /products?name=xyz) that matches nothing is 200 with an empty array, because the collection itself exists.

Why does JSON serialization produce camelCase and how do I change it?

ASP.NET Core defaults to JsonSerializerDefaults.Web (camelCase, case-insensitive reads). Change it with AddJsonOptions(o => o.JsonSerializerOptions.PropertyNamingPolicy = null). Enums as strings: add JsonStringEnumConverter. Use [JsonPropertyName] for one-off names.

How do I run EF migrations automatically in production?

Avoid Database.Migrate() at app start on multiple instances (race conditions, startup failures hurt availability). Prefer generating an idempotent script (dotnet ef migrations script --idempotent) or a migration bundle (dotnet ef migrations bundle) executed as a separate deployment step.

How do I call another API from my API correctly?

Use IHttpClientFactory (typed or named clients, or a generated NSwag client) so sockets and DNS are managed. Never new HttpClient() per request (socket exhaustion) nor a static one without PooledConnectionLifetime. Add resilience (Microsoft.Extensions.Http.Resilience / Polly: timeout, retry with jitter, circuit breaker), propagate the CancellationToken and correlation id.

What is the difference between AddControllers and AddMvc?

AddControllers registers only what an API needs (no Razor views). AddControllersWithViews adds views; AddMvc/AddRazorPages add pages. Use the smallest one for an API.

Minimal APIs or controllers for a new project?

Both run on the same endpoint-routing, DI and middleware infrastructure. Controllers give conventions, filters, model-binding extensibility and mature tooling; Minimal APIs are lighter and good for small services or vertical-slice designs (endpoint filters, route groups, typed Results). Pick one style per project for consistency.

How do I read the current user's id in a controller or service?

In a controller: User.FindFirstValue(ClaimTypes.NameIdentifier). In a service, inject IHttpContextAccessor (register with AddHttpContextAccessor()) or, better, a small ICurrentUser abstraction built on it so the domain layer does not depend on HTTP.

How do I make long-running work (reports, emails) not block the request?

Return 202 Accepted with a status URL and process in the background: a hosted BackgroundService reading from a Channel<T>, or a durable queue (Azure Service Bus, RabbitMQ) with a worker. Do not use fire-and-forget Task.Run with scoped services (the scope is disposed after the response).

How do I test an API?

Unit-test services with mocks; integration-test the whole pipeline with WebApplicationFactory<Program> (replace the DB with SQLite in-memory/Testcontainers and register a test auth handler); contract-test the OpenAPI document (oasdiff) to catch breaking changes.

Scenario 1 – Multi-tenant SaaS API

ProblemOne deployment serves many customers; data must never leak across tenants.

  • Apply an EF Core global query filter so every query is tenant-scoped automatically; stamp the tenant id in SaveChanges.
public interface ITenantProvider { Guid TenantId { get; } }

public sealed class ClaimsTenantProvider(IHttpContextAccessor accessor) : ITenantProvider
{
    public Guid TenantId => Guid.Parse(
        accessor.HttpContext!.User.FindFirstValue("tenant_id")
        ?? throw new UnauthorizedAccessException("tenant_id claim missing"));
}

public class AppDbContext(DbContextOptions<AppDbContext> options, ITenantProvider tenant) : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        // Evaluated per DbContext instance, so TenantId is the current request's tenant
        b.Entity<Order>().HasQueryFilter(o => o.TenantId == tenant.TenantId);
    }

    public override Task<int> SaveChangesAsync(CancellationToken ct = default)
    {

Scenario 2 – Idempotent payment/order creation

ProblemA mobile client times out and retries POST /orders; we must not charge twice.

Client sends a unique Idempotency-Key. The server stores key → response for 24h; a repeated key returns the stored result instead of executing again. Enforce uniqueness with a DB unique index so two concurrent retries cannot both succeed.

public sealed class IdempotentAttribute : Attribute, IAsyncActionFilter
{
    public async Task OnActionExecutionAsync(ActionExecutingContext ctx, ActionExecutionDelegate next)
    {
        if (!ctx.HttpContext.Request.Headers.TryGetValue("Idempotency-Key", out var key) || key.Count == 0)
        {
            ctx.Result = new BadRequestObjectResult(new ProblemDetails { Title = "Idempotency-Key header required" });
            return;
        }

        var cache = ctx.HttpContext.RequestServices.GetRequiredService<IDistributedCache>();
        var cacheKey = $"idem:{ctx.HttpContext.User.FindFirstValue(ClaimTypes.NameIdentifier)}:{key}";

        var saved = await cache.GetStringAsync(cacheKey);
        if (saved is not null)
        {
            ctx.Result = new ContentResult { Content = saved, ContentType = "application/json", StatusCode = 200 };
            return;                                   // replay stored response, do not run the action
        }

        var executed = await next();
        if (executed.Result is ObjectResult { StatusCode: >= 200 and < 300 } ok)
            await cache.SetStringAsync(cacheKey, JsonSerializer.Serialize(ok.Value),
                new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(24) });
    }
}

Scenario 3 – Safe file upload

  • Limit size ([RequestSizeLimit], Kestrel MaxRequestBodySize) and stream rather than buffering large files.
  • Validate extension and content signature (magic bytes); never trust Content-Type or the original file name.
  • Generate your own file name, store outside the web root (blob storage), scan for malware, serve through a controller or signed URL.
[HttpPost("avatar")]
[RequestSizeLimit(2 * 1024 * 1024)]
public async Task<IActionResult> Upload(IFormFile file, [FromServices] IBlobStore store, CancellationToken ct)
{
    var allowed = new Dictionary<string, byte[]> { [".png"] = [0x89, 0x50, 0x4E, 0x47], [".jpg"] = [0xFF, 0xD8, 0xFF] };
    var ext = Path.GetExtension(file.FileName).ToLowerInvariant();
    if (!allowed.TryGetValue(ext, out var magic)) return BadRequest("Unsupported type");

    await using var stream = file.OpenReadStream();
    var header = new byte[magic.Length];
    if (await stream.ReadAsync(header, ct) < magic.Length || !header.SequenceEqual(magic))
        return BadRequest("Content does not match extension");
    stream.Position = 0;

    var name = $"{Guid.NewGuid():N}{ext}";                // our own name: no path traversal
    await store.SaveAsync(name, stream, ct);
    return Created($"/api/uploads/{name}", new { name });
}

Operational checklist

  • ☐ TLS everywhere; HSTS enabled; no mixed content.
  • ☐ Secrets in a vault; rotate signing keys; use asymmetric keys (RS256/ES256) when many services verify tokens.
  • ☐ Access tokens ≤ 15 min; refresh tokens hashed, rotated, with reuse detection and absolute lifetime.
  • ☐ Passwords hashed with PBKDF2/Argon2/bcrypt; login rate-limited with generic error messages.
  • ☐ Every query filtered by the caller's ownership/tenant; negative tests for 401/403/404 across users.
  • ☐ CORS limited to known origins; credentials allowed only when required.
  • ☐ Swagger UI disabled or protected in production.
  • ☐ Dependencies scanned (dotnet list package --vulnerable); SAST/DAST in CI.
  • ☐ Audit logging of auth events and admin actions without logging secrets.
  • ☐ Request size, timeout, rate limit and paging limits configured.

[HttpGet("{id:int}")]
public async Task<IActionResult> Get(int id, CancellationToken ct)
{
    var p = await db.Products.AsNoTracking().FirstOrDefaultAsync(x => x.Id == id, ct);
    if (p is null) return NotFound();

    var etag = $"\"{Convert.ToHexString(p.RowVersion)}\"";
    if (Request.Headers.IfNoneMatch == etag) return StatusCode(StatusCodes.Status304NotModified);   // no body sent

    Response.Headers.ETag = etag;
    Response.Headers.CacheControl = "private, max-age=30";
    return Ok(p.ToDto());
}

Ten sentences to remember

  1. Keep controllers thin; put logic in services and return DTOs, never entities.
  2. Middleware order is behaviour: exception → HTTPS → CORS → authentication → authorization → endpoints.
  3. Authenticate to know who; authorize to decide what; 401 and 403 are different.
  4. Short-lived JWT + rotating refresh token is the standard stateless pattern.
  5. Never trust input: validate, bind to DTOs, parameterise queries, check ownership on every object.
  6. Async all the way, with cancellation tokens.
  7. Return ProblemDetails and the right status codes consistently.
  8. Version from day one and deprecate gracefully.
  9. Document with OpenAPI, and generate clients from it – the contract is the source of truth.
  10. Measure before optimising; cache and project data before adding hardware.
